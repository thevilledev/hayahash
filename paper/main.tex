\title{Hayahash: A Portable Scalar Non-Cryptographic Hash\\
with 64- and 128-bit Digests}
\author{Ville Vesilehto}
\date{Working draft, \SnapshotDate}

\begin{document}

\maketitle

\begin{abstract}
Hayahash is an experimental, seeded, non-cryptographic hash function for
targets that have ordinary 64-bit multiplication but no cheap 128-bit
product and no guaranteed SIMD.  Its bulk loop keeps the loop-carried
dependency chain to an XOR followed by a multiplication, spread over eight
independent lanes.  Adjacent input words are linked by a chained
add-and-rotate transform that is bijective on the whole stripe sequence,
so no structural difference pattern can cancel inside the absorb.  The
input length is absorbed in the finalizer rather than the initial state,
which makes the digest a pure function of the seed and the bytes read so
far and permits a streaming interface that reproduces the one-shot digest
exactly.  A 128-bit variant extracts a second word from the same state
walk; its low word equals the 64-bit digest for every input and seed, and
on inputs of at most 16 bytes the 128-bit map is injective for each fixed
length and seed.  This paper specifies the current development snapshot,
proves the structural properties the design relies on, explains the
reasoning behind each mechanism, and records the available quality and
performance evidence.  Both digest widths pass SMHasher3's default suite,
and the recorded benchmarks lead ChibiHash v2, the closest function in the
same primitive class, on the measured systems.  There is no proof for the
complete construction and no cryptographic security claim.
\end{abstract}

\section{Introduction}

\subsection{Motivation}
\label{sec:motivation}

The fastest current 64-bit hash functions obtain their speed from one of
two hardware assumptions.  Designs in the wyhash line, including its
successor rapidhash, fold the two halves of a $64\times64\to128$-bit
product into their state and depend on that widening multiplication being
cheap \cite{wang2021wyhash,nicoshev2025rapidhash}.  Vectorized designs,
including the fast paths of the xxHash family, depend on SIMD widths and
instruction sets that are negotiated per target
\cite{collet2023xxhashspec}.

Both assumptions fail on real targets.  Baseline WebAssembly has
\texttt{i64.mul} but neither a 128-bit product nor guaranteed SIMD.  The
portable subsets of C used for reference implementations, small in-order
cores, and older 64-bit server processors are in the same position.  The
cost of the missing primitive is not marginal.  In the archived
WebAssembly comparison (Section~\ref{sec:bench}), rapidhash sustains
6.43~GB/s where Hayahash sustains 23.55~GB/s in the same runtime on the
same machine: the widening product that rapidhash relies on must be
synthesized from four narrow multiplications, and its speed does not
survive the translation.

There is a second, independent reason to restrict the primitive set.  A
hash that is deployed across many language runtimes must produce one exact
digest everywhere.  Every primitive the algorithm requires must therefore
exist, with identical semantics, in every port: C, Rust, Go, Zig, Java,
C\#, Python, Swift, JavaScript, and WebAssembly.  Unsigned 64-bit
addition, XOR, rotation, shifts, and the low
half of multiplication meet that bar.  A widening multiply, carry flags,
or vector permutes do not; each port would reimplement them differently,
and the fast path would again be negotiated per target.

Hayahash explores the resulting question: how fast can a 64-bit hash be
when it is restricted to portable scalar operations and the low half of
64-bit multiplication, with alignment-safe reads and a result independent
of host byte order?

\subsection{The construction and why it is shaped this way}
\label{sec:case}

Four decisions carry the design.  Each is stated here with its reason;
Section~\ref{sec:rationale} develops the reasoning in full and
Section~\ref{sec:properties} proves what can be proved.

\textbf{The bulk loop is latency-bound on nothing longer than add and
multiply.}  On a wide out-of-order core, the throughput limit of a scalar
hash loop is the loop-carried dependency chain of each lane divided by the
number of independent lanes.  Hayahash's bulk loop runs eight lanes over
64-byte blocks; the carried path per lane is one XOR and one
multiplication, roughly four cycles, with no cross-lane operation on the
carried path.  ChibiHash v2, the closest published function in the same
primitive class, carries a chain of roughly five cycles per 8-byte stripe
across four lanes because a cross-lane addition sits on its carried path
\cite{nrk2024chibihash}.  The measured consequence at 1~MiB is
30.73 versus 18.99~GB/s on an Apple M1 performance core and 61.47 versus
31.13~GB/s on a Zen~5 core (Section~\ref{sec:bench}).

\textbf{The absorb transform is chained, and the chain is bijective.}
Each stripe is absorbed as $t_i = w_i + \rotl(w_{i-1},27)$, where
$w_{i-1}$ is the previous raw input word, carried across lane, block, and
loop boundaries.  The map from the word sequence to the absorbed sequence
is a bijection (Lemma~\ref{lem:chain}), so no difference pattern in the
input can cancel to nothing inside the absorb values themselves; an
earlier variant that combined staggered word copies by XOR was
GF(2)-linear and had a nullspace, which produced constructed collisions.
The rotated copy also plants every stripe's bits at low positions of the
next stripe's absorb, where addition and rotation mix two incompatible
algebras; cancelling both copies of a difference simultaneously requires
matching carries by luck rather than by structure
(Section~\ref{sec:rationale-absorb}).  The rotation is applied to a word
that is already in a register and sits off the carried path, so the
mechanism is latency-free.

\textbf{The length is absorbed in the finalizer, not the initial state.}
Every lane's initial value is derived from the seed alone, so the internal
state after $k$ bytes depends only on the seed and those $k$ bytes.  This
purity is what makes a streaming interface with one-shot-identical digests
possible at all; the previous spelling premixed $n$ into the initial
state, and a streaming state would have needed the total length before the
first byte.  The length enters as $nK$ inside a multiplication in the
finalizer.  Multiplication by the odd constant $K$ makes $n \mapsto nK$
injective, and Lemma~\ref{lem:length} shows that inputs of different
lengths that reach the finalizer with identical state still produce
different digests in both output words.  That is the property that makes
the overlapping tail reads safe: all-zero inputs of lengths 17 through 31,
for example, produce identical absorb sequences and are separated by the
length term alone.  The simpler spelling that XORs $nK$ after the final
multiplications leaves modular low-bit structure across lengths and fails
SMHasher3's SeedZeroes differentials; the chosen spelling costs no
additional multiplication.

\textbf{Tails read overlapping whole words; short inputs take a dedicated
two-multiply path.}  Inputs longer than 16 bytes are consumed only as
whole 64-bit words, with the final reads taken from the end of the input
at overlapping offsets, a technique adopted from wyhash
\cite{wang2021wyhash}; no byte-at-a-time loop exists for any length.
Inputs of at most 16 bytes load two words, spread each through a different
bijective three-rotation injection, multiply each by a different odd
constant, and merge through a strong finalizer.  For the 128-bit digest
this path is injective for every fixed length and seed
(Theorem~\ref{thm:short128}), and on exactly 16-byte inputs it is a
permutation of the 128-bit space.

Two further properties fall out of the same state walk rather than being
bolted on.  The 128-bit digest reuses the identical absorb and fold
sequence and extracts a second word at the end; its low word equals the
64-bit digest for every input and seed, and its marginal cost is confined
to the finalizer.  The streaming interface buffers at most 448 bytes,
consumes input in the exact block order of the one-shot function, and
reproduces both digest widths bit for bit under every split of the input;
this is proved as Proposition~\ref{prop:streaming} and checked by a
differential test that replays fixed and randomized split patterns.

The design was hardened by failure.  SMHasher3 \cite{wojcik2022smhasher3}
found five distinct structural collision classes in earlier iterations:  a
GF(2) nullspace in a staggered-load absorb, seed-copy erasure by aligned
key bits in two forms, carry-matched difference ladders, and a fold
rotation that resonated with the absorb rotation.  Each current mechanism
that responds to one of these failures is documented with the failure that
produced it (Section~\ref{sec:failures}), and a deterministic regression
for the constructed rotation-orbit family is kept in the test suite.

\subsection{Scope and non-goals}

Hayahash maps a byte string and a 64-bit seed to a 64-bit or 128-bit
result.  The intended uses are hash tables, checksums internal to a
process, and similar non-adversarial tasks.  It is not intended for
passwords, signatures, message authentication, untrusted hash-table keys,
or any use that requires collision or preimage resistance.  The seed is an
input, not a secret-key security mechanism.  The algorithm is
experimental: constants, thresholds, and digest values may change between
releases, and nothing should persist Hayahash values yet.

The design constraints are:

\begin{itemize}
\item unsigned 64-bit scalar arithmetic;
\item ordinary multiplication modulo \(2^{64}\), without the high product;
\item no required SIMD or architecture-specific instruction extension;
\item alignment-safe reads and a result independent of host byte order;
      and
\item one reference mapping across all supported implementations.
\end{itemize}

The C source contains architecture- and compiler-specific scheduling
choices.  These use the same operations and are specified to preserve the
digest.  The portability claim concerns required primitives and output,
not identical source code on every target.

\section{Related work}
\label{sec:related}

MurmurHash3 established the pattern of multiply-and-rotate scalar mixing
with a strong bijective finalizer \cite{appleby2011murmurhash3}; its
64-bit finalizer constants are reused in Hayahash's 128-bit output path,
and the short-input finalizer is Evensen's \texttt{moremur} refinement of
the same shape \cite{evensen2018moremur}.  The xxHash family documents the
scalar and vectorized state of the art and its verification discipline
\cite{collet2023xxhashspec}.  wyhash and rapidhash define the current
speed frontier on hardware with a cheap widening multiplication
\cite{wang2021wyhash,nicoshev2025rapidhash}; they are outside Hayahash's
primitive class, and Section~\ref{sec:bench} shows what happens to that
frontier on a target without the primitive.

ChibiHash v2 is the baseline used throughout this paper because it
occupies the same narrow implementation class: a small, portable, scalar
64-bit function using the low half of ordinary multiplication
\cite{nrk2024chibihash}.  The comparison is therefore between design
choices, not between primitive sets.  Hayahash also borrows directly from
it: the 1-to-3-byte load pattern is ChibiHash v2's, and ChibiHash v1 used
the same \texttt{moremur} finalizer.

Empirical test suites and mathematical guarantees are separate kinds of
evidence.  SMHasher3 tests distribution, collisions on generated key sets,
and performance \cite{wojcik2022smhasher3}; a clean run does not prove
collision resistance, and Section~\ref{sec:smhasher} records a concrete
case where a clean run coexisted with a constructed collision.  At the
other end, PolymurHash states an almost-universality bound under an
explicit model \cite{peters2023polymurhash}.  Hayahash currently has no
comparable bound, and Section~\ref{sec:limitations} lists producing one,
or documenting why the construction does not admit one, as open work.

\section{Notation and interface contract}
\label{sec:contract}

All state values are unsigned 64-bit words.  Addition, multiplication, and
left shift discard bits above bit 63.  Right shift is logical.
\(\rotl(x,r)\) rotates a word left by \(r\) bits.  \(\load(B,p)\) reads
eight bytes starting at offset \(p\) of buffer \(B\), with the first byte
as the least significant byte; a corresponding four-byte load is
zero-extended.  The implementation realizes these loads with
\texttt{memcpy} and byte swaps on known big-endian hosts, or explicit
byte assembly when no byte-order macro exists, so no alignment or
endianness assumption leaks into the digest.

The constants are:

\begin{align*}
K   &= \mathtt{9E3779B97F4A7C15}_{16}, &&\text{\(\lfloor 2^{64}/\varphi
\rfloor\), odd,}\\
M_1 &= \mathtt{3C79AC492BA7B653}_{16}, &&\text{\texttt{moremur}
multiplier,}\\
M_2 &= \mathtt{1C69B3F74AC4AE35}_{16}, &&\text{\texttt{moremur}
multiplier,}\\
N_1 &= \mathtt{FF51AFD7ED558CCD}_{16}, &&\text{MurmurHash3 finalizer
multiplier,}\\
N_2 &= \mathtt{C4CEB9FE1A85EC53}_{16}, &&\text{MurmurHash3 finalizer
multiplier.}
\end{align*}

All five constants are odd.  The input length \(n\) must be non-negative,
and the caller must provide \(n\) readable bytes; a null pointer is
permitted only when \(n=0\).

Two linear word injections are used:

\begin{align*}
\inj(w)  &= w \oplus \rotl(w,21) \oplus \rotl(w,41),\\
\injb(w) &= w \oplus \rotl(w,11) \oplus \rotl(w,50).
\end{align*}

Three finalizers are used.  \texttt{fmix} is the \texttt{moremur} map
\cite{evensen2018moremur}, \texttt{fmix128} is the MurmurHash3 finalizer
\cite{appleby2011murmurhash3}, and \texttt{long\_fmix} is a single-multiply
avalanche used after the long paths:

\begin{lstlisting}
fmix(x):                fmix128(x):             long_fmix(x):
    x ^= x >> 27            x ^= x >> 30            x ^= x >> 37
    x *= M1                 x *= N1                 x *= K
    x ^= x >> 33            x ^= x >> 31            x ^= x >> 32
    x *= M2                 x *= N2                 return x
    x ^= x >> 27            x ^= x >> 33
    return x                return x
\end{lstlisting}

\section{Specification}
\label{sec:spec}

Every path begins with the seed premix and the length term
\[
    s = \mathit{seed} \oplus K, \qquad \mathit{lenmix} = nK .
\]
The length appears nowhere else: the initial state depends on the seed
alone, and \(\mathit{lenmix}\) is consumed by the finalizer.

Three length regimes exist.  Inputs of at most 16 bytes take the short
path; inputs of 17 to 319 bytes run four lanes over 32-byte blocks;
inputs of at least 320 bytes run eight lanes over 64-byte blocks and then
fall through to the four-lane machinery for the remainder.

\subsection{Inputs of at most 16 bytes}
\label{sec:spec-short}

Two words \(a\) and \(b\) are formed without reading outside the input:

\begin{lstlisting}
if n >= 8:
    a = load64le(B, 0)
    b = load64le(B, n - 8)
else if n >= 4:
    a = load32le(B, 0)
    b = load32le(B, n - 4)
else if n > 0:
    a = B[0]
    b = (B[n / 2] << 8) | (B[n - 1] << 16)
else:
    a = 0
    b = 0
\end{lstlisting}

The head and end reads overlap for some lengths; this is intentional, and
Lemma~\ref{lem:length} is what makes it safe.  The two words are spread by
different injections, combined with different seed derivations, and
multiplied by different odd constants:

\begin{align*}
x &= (\inj(a) \oplus s \oplus K)\,K,\\
y &= (\injb(b) \oplus \rotl(s,23) \oplus (K \mathbin{\gg} 19))\,M_1.
\end{align*}

The 64-bit result is
\[
    \operatorname{fmix}(\rotl(x,27) \oplus y \oplus \mathit{lenmix}).
\]

\subsection{The absorb chain}
\label{sec:spec-absorb}

All longer inputs consume the input as a sequence of 64-bit words
\(w_0, w_1, \ldots\) called stripes.  Let \(w_p\) be the previous stripe,
initially zero.  One stripe is absorbed into a lane \(h\) as

\begin{lstlisting}
absorb(h, w):
    h = (h ^ (w + rotl(wp, 27))) * K
    wp = w
\end{lstlisting}

The addition happens before the XOR with the lane.  The previous stripe
carries across lane boundaries, block boundaries, and the boundary
between the eight-lane and four-lane loops.

\subsection{Inputs of 17 to 319 bytes}
\label{sec:spec-mid}

The four-lane state is derived from \(s\) and shifted copies of \(K\):

\begin{align*}
h_0 &= s \oplus K, &
h_1 &= \rotl(s,17) + (K \mathbin{\ll} 21),\\
h_2 &= \rotl(s,34) \oplus (K \mathbin{\gg} 13), &
h_3 &= \rotl(s,51) + (K \mathbin{\ll} 42).
\end{align*}

Each complete 32-byte block absorbs four consecutive stripes into
\(h_0,h_1,h_2,h_3\) in that order.  The remainder \(r < 32\) then goes to
the wall and tail (Section~\ref{sec:spec-tail}).

\subsection{Inputs of at least 320 bytes}
\label{sec:spec-bulk}

Four more lanes are initialized:

\begin{align*}
h_4 &= s + (K \mathbin{\gg} 27), &
h_5 &= \rotl(s,13) \oplus (K \mathbin{\ll} 9),\\
h_6 &= \rotl(s,26) + (K \mathbin{\gg} 40), &
h_7 &= \rotl(s,39) \oplus (K \mathbin{\ll} 30).
\end{align*}

Each complete 64-byte block absorbs eight consecutive stripes into
\(h_0,\ldots,h_7\).  After the eighth absorb of every block, the raw
eighth stripe is added to \(h_0\):
\[
    h_0 \mathrel{+}= w_p .
\]
This checkpoint is part of the digest
(Section~\ref{sec:rationale-rotation}).  After the last complete 64-byte
block, the upper lanes are folded into the lower lanes:

\begin{align*}
h_0 &\leftarrow (h_0 \oplus \rotl(h_4,11))\,K, &
h_1 &\leftarrow (h_1 \oplus \rotl(h_5,19))\,K,\\
h_2 &\leftarrow (h_2 \oplus \rotl(h_6,31))\,K, &
h_3 &\leftarrow (h_3 \oplus \rotl(h_7,47))\,K.
\end{align*}

If at least 32 bytes remain, one four-lane block is then processed; the
previous-stripe chain continues across the fold.  The remainder \(r < 32\)
goes to the wall and tail.

The threshold of 320 bytes is an algorithm parameter, not a tuning knob.
An input of exactly 320 bytes takes the eight-lane path and processes five
complete blocks; moving the threshold changes digests.  Its value also
keeps the four-lane path shorter than the absorb rotation's 64-stripe
orbit (Section~\ref{sec:rationale-rotation}).

\subsection{Wall, tail, and finalizer}
\label{sec:spec-tail}

After the complete-block loops, the final stripe's dangling rotated copy
is absorbed:
\[
    h_0 \mathrel{+}= \rotl(w_p,27).
\]
This operation is called the wall.  It is a no-op when no complete stripe
was processed, because \(w_p\) is then still zero.

Let \(p\) be the offset of the first unconsumed byte and \(r\) the
remaining length, \(0 \leq r < 32\) on both paths.  The tail absorbs whole
words through the bijective injection \(\inj\):

\begin{lstlisting}
if r > 16:
    h0 = (h0 + inj(load64le(B, p + 0))) * K
    h1 = (h1 + inj(load64le(B, p + 8))) * K

if r > 0:
    h2 = (h2 + inj(load64le(B, n - 16))) * K
    h3 = (h3 + inj(load64le(B, n - 8))) * K
\end{lstlisting}

The last two reads always cover the final 16 bytes of the input and may
overlap bytes that were already absorbed; at \(r = 0\) there are no tail
reads at all.  The finalizer folds the lanes, absorbs the length term
inside the first multiplication, and avalanches:

\begin{align*}
t_0 &= (h_0 \oplus \rotl(h_1,13) \oplus \mathit{lenmix})\,K,\\
t_1 &= (h_2 \oplus \rotl(h_3,33))\,K,\\
z   &= s \oplus t_0 \oplus \rotl(t_1,29).
\end{align*}

The 64-bit result is \(\operatorname{long\_fmix}(z)\).

\subsection{The 128-bit digest}
\label{sec:spec-128}

hayahash128 runs the identical state walk and extracts two words at the
end, so producing both words needs no second pass over the input.  On the
short path, with \(x\), \(y\), and \(\mathit{lenmix}\) as in
Section~\ref{sec:spec-short} and
\(u = \rotl(x,27) \oplus y \oplus \mathit{lenmix}\):

\begin{align*}
\mathit{lo} &= \operatorname{fmix}(u),\\
\mathit{hi} &= \operatorname{fmix128}(x + \rotl(u,32)).
\end{align*}

On the longer paths, with \(t_0\) and \(t_1\) as in
Section~\ref{sec:spec-tail}:

\begin{align*}
\mathit{lo} &= \operatorname{long\_fmix}(s \oplus t_0 \oplus
\rotl(t_1,29)),\\
\mathit{hi} &= \operatorname{fmix128}(\rotl(s,32) \oplus (t_1 +
\rotl(t_0,47))).
\end{align*}

The low word is exactly hayahash64 for every input and seed.  The high
word combines \(t_0\) and \(t_1\) with addition where the low word uses
XOR, so a single GF(2)-linear cancellation cannot erase a difference from
both output words, and it is finalized by a different bijection.

\subsection{The streaming interface}
\label{sec:spec-streaming}

The streaming state holds the eight lanes, the previous stripe, the seed,
the running total, and a 448-byte buffer with a 128-byte retention floor.
\texttt{update} appends bytes; \texttt{digest} may be called at any time,
does not modify the state, and returns either digest width.  Two
invariants govern the buffer: bytes are consumed only in whole 64-byte
blocks, in one-shot block order from stream offset zero, and at digest
time the buffer always retains at least 128 trailing bytes, which contains
every address the tail reads.  Totals below 448 bytes remain fully
buffered and dispatch to the one-shot function at digest time.
Proposition~\ref{prop:streaming} states the resulting guarantee: both
digest widths equal their one-shot values under every split of the input
into update calls.

\section{Structural properties}
\label{sec:properties}

This section proves the properties the construction relies on.  The scope
of each statement is deliberately narrow, and the section ends by stating
what is not proved.  Throughout, arithmetic is modulo \(2^{64}\) and
\(\mathbb{W} = \{0,1\}^{64}\) is the set of 64-bit words.

\begin{lemma}[Absorb chain bijectivity]
\label{lem:chain}
Fix \(w_{-1} \in \mathbb{W}\) and \(m \geq 0\), and define
\(\Phi(w_0,\ldots,w_m) = (t_0,\ldots,t_m)\) with
\(t_i = w_i + \rotl(w_{i-1},27)\).  Then \(\Phi\) is a bijection on
\(\mathbb{W}^{m+1}\).  Moreover, if two stripe sequences first differ at
index \(j\), their images agree before index \(j\) and differ at index
\(j\).
\end{lemma}

\begin{proof}
Given \((t_0,\ldots,t_m)\), the preimage is recovered in order:
\(w_0 = t_0 - \rotl(w_{-1},27)\), and
\(w_i = t_i - \rotl(w_{i-1},27)\) once \(w_{i-1}\) is known.  So \(\Phi\)
is invertible.  For the second claim, if the sequences agree before index
\(j\), the images agree there and the values \(w_{j-1}\) coincide, so
\(t_j = w_j + \rotl(w_{j-1},27)\) differs exactly when \(w_j\) differs,
because adding a fixed word is injective.
\end{proof}

Consequently, two distinct inputs that disagree in some stripe always feed
the lane machinery different absorb values at the first differing stripe:
no difference pattern cancels inside the transformed sequence.  The lemma
says nothing about what the lane recurrence and folds do with those
values afterward.

\begin{lemma}[Injection bijectivity]
\label{lem:inj}
For \(0 < a < b < 64\), the map
\(\iota(w) = w \oplus \rotl(w,a) \oplus \rotl(w,b)\) is a bijection on
\(\mathbb{W}\).  In particular \(\inj\) and \(\injb\) are bijections.
\end{lemma}

\begin{proof}
\(\iota\) is GF(2)-linear and commutes with rotation, so it lies in the
algebra \(\mathbb{F}_2[z]/(z^{64}+1)\), with \(\rotl(\cdot,k)\)
corresponding to \(z^k\) and \(\iota\) to \(p(z) = 1 + z^a + z^b\).  Over
\(\mathbb{F}_2\), \(z^{64}+1 = (z+1)^{64}\), so \(p\) is invertible in the
algebra if and only if \(z+1\) does not divide \(p\), that is
\(p(1) \neq 0\).  Since \(p\) has three terms, \(p(1) = 1\).
\end{proof}

\begin{lemma}[Finalizer bijectivity]
\label{lem:fmix}
The maps \(x \mapsto x \oplus (x \mathbin{\gg} k)\) for
\(1 \leq k \leq 63\) and \(x \mapsto cx\) for odd \(c\) are bijections on
\(\mathbb{W}\).  Hence \(\operatorname{fmix}\),
\(\operatorname{fmix128}\), and \(\operatorname{long\_fmix}\) are
bijections.
\end{lemma}

\begin{proof}
For the shift map, the top \(k\) bits of the image equal the top \(k\)
bits of the argument, and each lower bit is the argument bit XOR an
already-recovered higher bit, so the argument is recovered from the top
down.  An odd \(c\) is a unit modulo \(2^{64}\).  The finalizers are
compositions of these maps.
\end{proof}

\begin{lemma}[Length separation]
\label{lem:length}
Fix a seed, and let two inputs have lengths \(n \neq n'\) with
\(0 \leq n, n' < 2^{63}\).
\begin{enumerate}
\item If both lengths are at most 16 and the inputs load equal word pairs
      \((a,b)\), then the 64-bit digests differ, and the 128-bit digests
      differ in the low word.
\item If both lengths are at least 17 and the inputs reach the finalizer
      with equal lane values \((h_0,h_1,h_2,h_3)\), then the 64-bit
      digests differ, and the 128-bit digests differ in both words.
\end{enumerate}
\end{lemma}

\begin{proof}
Since \(K\) is odd, \(n \mapsto nK\) is injective on \(\mathbb{W}\), and
lengths below \(2^{63}\) are distinct as words, so
\(\mathit{lenmix} \neq \mathit{lenmix}'\).

Case 1.  Equal \((a,b)\) and equal seed give equal \((x,y)\), so the
finalizer inputs \(u = \rotl(x,27) \oplus y \oplus \mathit{lenmix}\) and
\(u'\) differ.  \(\operatorname{fmix}\) is a bijection
(Lemma~\ref{lem:fmix}), so the low words differ.

Case 2.  Equal lane values give equal
\(h_0 \oplus \rotl(h_1,13)\), so
\(t_0 = (h_0 \oplus \rotl(h_1,13) \oplus \mathit{lenmix})K\) and
\(t_0'\) differ: their pre-multiplication values differ and
multiplication by odd \(K\) is injective.  \(t_1 = t_1'\).  The low-word
finalizer input \(s \oplus t_0 \oplus \rotl(t_1,29)\) then differs, and
\(\operatorname{long\_fmix}\) is a bijection.  The high-word input
\(\rotl(s,32) \oplus (t_1 + \rotl(t_0,47))\) differs because
\(\rotl(\cdot,47)\) is injective and adding the fixed \(t_1\) is
injective, and \(\operatorname{fmix128}\) is a bijection.
\end{proof}

The lemma covers exactly the collision class that overlapping reads
create.  Distinct-length inputs can produce identical loaded words and
identical absorb sequences; the concrete extreme is all-zero inputs of
lengths 17 through 31, whose lane states are identical at the finalizer.
Within each path family, such pairs never collide.  No claim is made for
pairs that take different paths with different state shapes; there the
inputs differ structurally and the empirical evidence of
Section~\ref{sec:evaluation} is what speaks.

\begin{theorem}[Short-input 128-bit injectivity]
\label{thm:short128}
Fix a seed and a length \(n \leq 16\).  The map from \(n\)-byte inputs to
the 128-bit digest \((\mathit{lo},\mathit{hi})\) is injective.
\end{theorem}

\begin{proof}
The map factors as
\(B \mapsto (a,b) \mapsto (x,y) \mapsto (u,x) \mapsto
(\mathit{lo},\mathit{hi})\).

\((a,b)\) determines \(B\):  for \(8 \leq n \leq 16\), \(a\) holds bytes
\(0..7\) and \(b\) holds bytes \(n-8..n-1\), and since \(n - 8 \leq 8\)
every input byte occupies a fixed position of \(a\) or \(b\); for
\(4 \leq n \leq 7\) the same holds with four-byte words; for
\(1 \leq n \leq 3\), \(a = B[0]\) and \(b\) holds \(B[n/2]\) and
\(B[n-1]\) in disjoint bit ranges, and the positions \(0\), \(n/2\),
\(n-1\) cover every index below \(n\); for \(n = 0\) the domain has one
element.  Two distinct inputs of length \(n\) therefore differ in some
fixed bit of \((a,b)\).

\((a,b) \mapsto (x,y)\) is a bijection for a fixed seed: each coordinate
composes a bijective injection (Lemma~\ref{lem:inj}), an XOR with a
constant, and a multiplication by an odd constant
(Lemma~\ref{lem:fmix}).

\((x,y) \mapsto (u,x)\) with
\(u = \rotl(x,27) \oplus y \oplus \mathit{lenmix}\) is a bijection for a
fixed length: \(y\) is recovered as
\(u \oplus \rotl(x,27) \oplus \mathit{lenmix}\).

\((u,x) \mapsto (\operatorname{fmix}(u),
\operatorname{fmix128}(x + \rotl(u,32)))\) is a bijection: \(u\) is
recovered from \(\mathit{lo}\) by Lemma~\ref{lem:fmix}, then \(x\) from
\(\mathit{hi}\).
\end{proof}

\begin{corollary}
For each seed, hayahash128 restricted to inputs of exactly 16 bytes is a
permutation of the 128-bit space, and restricted to inputs of exactly 8
bytes it is injective into it.
\end{corollary}

No analogous claim holds for the 64-bit digest alone, which discards
\(x\), nor across distinct lengths, nor above 16 bytes; a 64-bit digest of
arbitrarily long inputs necessarily has collisions.

\begin{proposition}[Streaming equivalence]
\label{prop:streaming}
For every seed, every byte sequence, and every partition of the sequence
into update calls, \texttt{hayahash64\_digest} equals
\texttt{hayahash64} of the whole sequence, and
\texttt{hayahash128\_digest} equals \texttt{hayahash128}.
\end{proposition}

\begin{proof}[Proof sketch]
If the total stays below the 448-byte buffer capacity, the bytes are still
contiguous in the buffer at digest time and the state dispatches to the
one-shot function directly.  Otherwise the total exceeds 320 bytes, so the
one-shot function would take the eight-lane path, and the state machine
has committed to the same path.  Update calls consume input only in
complete 64-byte blocks, in stream order from offset zero, through the
identical absorb-and-checkpoint block transform; this matches the one-shot
path, which consumes complete 64-byte blocks while at least 64 bytes
remain.  At digest time the remaining buffered bytes replay the one-shot
epilogue on a copy of the lanes: leftover complete blocks, the fold, at
most one 32-byte round, the wall, the tail, and the finalizer with
\(\mathit{lenmix}\) computed from the running total.  The buffer's
128-byte retention floor guarantees the buffered suffix contains the last
16 bytes of the stream, which is the deepest address the tail reads back;
all other reads are within the unconsumed remainder.  Since the operation
sequences are identical and every read returns the same byte, the digests
agree, for both widths, and \texttt{digest} reads the state without
modifying it.
\end{proof}

The mechanical check of this proposition is part of the test suite: a
differential test replays every length through 512 under three seeds and
five fixed split patterns, plus 1{,}000 randomized cases through 20~KiB
under three split distributions, and requires one-shot and streaming
equality for both widths together with the invariant
\(\mathtt{hayahash128.lo} = \mathtt{hayahash64}\).

\textbf{What is not proved.}  The lemmas above are local.  They do not
bound collisions of the complete construction: the lane recurrence, the
folds, and the 64-bit truncation are outside their scope.  Hayahash has no
almost-universality bound and no adversarial guarantee of any kind.  The
value of the lemmas is negative-space: they close the specific structural
collision channels that broke earlier iterations, and they delimit exactly
where only empirical evidence exists.

\section{Design rationale}
\label{sec:rationale}

\subsection{The dependency-chain budget}
\label{sec:rationale-chain}

A scalar bulk loop is bound either by its loop-carried dependency chains
or by execution throughput.  Per lane, Hayahash's carried path is
\(h \leftarrow (h \oplus t)\,K\): one XOR and one multiplication, roughly
four cycles on current cores.  The absorb value \(t\) is computed from
loaded stripes off the carried path, and the rotation applies to a word
already in a register, so neither lengthens the chain.  With a chain of
roughly four cycles, eight lanes can keep two multiplications in flight
per cycle, which matches the scalar multiply throughput of current wide
cores and leaves headroom for loads and loop overhead; four lanes can
keep only one in flight, leaving a single-multiplier core no headroom at
all.  This is the reason for eight lanes on the bulk path and four on the
mid path, where inputs are too short to amortize the wider state's setup
and fold.

The comparison function in the same primitive class, ChibiHash v2, keeps a
cross-lane addition on its carried path, which makes the chain roughly
five cycles per 8-byte stripe across four lanes.  The measured outcome at
1~MiB, 30.73 versus 18.99~GB/s on the M1 and 61.47 versus 31.13~GB/s on
Zen~5, is consistent with the chain arithmetic.  This is a scheduling
rationale, not a portable cycle-count guarantee; instruction latency,
register allocation, and code layout vary by compiler and target, which is
why the C implementation carries output-equivalent per-target
specializations.

An earlier design absorbed each stripe twice by loading it at two
staggered offsets.  Beyond its algebraic failure
(Section~\ref{sec:failures}), it was load-bound: three loads per 16 input
bytes were the measured throughput limiter on the M1.  The chained
rotation replaced the second load with one register operation.

\subsection{Why the absorb chains raw stripes}
\label{sec:rationale-absorb}

The absorb must prevent structural cancellation: a difference pattern
across stripes that erases itself in the state regardless of the input
values.  Two facts about multiplication modulo \(2^{64}\) shape the
mechanism.  First, an odd multiplier spreads a difference only upward: the
lowest set bit of \(\Delta \cdot K\) is the lowest set bit of \(\Delta\).
Second, the top of the word is a fixed point: since \(K \equiv 1 \pmod 4\),
any difference confined to bits 62 and 63 is preserved exactly by
multiplication by \(K\).  A difference planted near the top therefore
stays there, un-avalanched, and an XOR-linked absorb could cancel it with
a matching top difference in a later stripe.

The response is to give every stripe a second life at low positions of the
next absorb: \(t_i = w_i + \rotl(w_{i-1},27)\).  Cancelling a stripe
difference now requires cancelling both the raw copy in \(t_i\) and the
rotated copy in \(t_{i+1}\).  The raw copy sits under an XOR into the
lane, the rotated copy under a modular addition; addition and rotation
commute with neither GF(2) algebra nor each other, so a difference that is
linear in one view is nonlinear in the other, and simultaneous
cancellation requires specific carry patterns, never a structural
identity.  Lemma~\ref{lem:chain} states the guarantee that holds
unconditionally: the transformed sequence itself never collides.  The
earlier XOR-of-staggered-copies variant had exactly the structural
identity this excludes; XOR-combining shifted stripe copies is
GF(2)-linear, and once absorbs chain, the combined map has a nullspace.

The tail rounds use the bijective injection \(\inj\) instead of the
chain.  A tail contributes at most two rounds per digest, each feeding its
own lane, so per-absorb bijectivity is sufficient there, and the injection
spreads each tail word across the full width before its multiplication.

\subsection{Rotation 27, the checkpoint, and the wall}
\label{sec:rationale-rotation}

The rotation amount is chosen against difference ladders.  A ladder flips
bits in stripe \(i+1\) to cancel, with carry luck, the rotated copy of a
difference in stripe \(i\); the residual difference then walks 27 bit
positions per stripe.  Because \(\gcd(27,64)=1\), the walk visits every
position with period 64 stripes.  Termination of a ladder requires the
walking difference to reach the multiplication's fixed region at the top
of the word in a stripe that lands in the same lane, so the relevant
revisits happen at stripe distances that are multiples of the lane count.
With \(r = 21\), three hops return to the top
(\(3 \cdot 21 = 63\)), and an earlier iteration produced exact collisions
through anchors of the form \(2^{62}(K-1) \equiv 0 \pmod{2^{64}}\).  With
\(r = 27\), every same-lane revisit stays far from the top for all
practical lengths.

Two mechanisms close the remaining exits.  The checkpoint adds the raw
eighth stripe to \(h_0\) after every 64-byte block; it was added after a
64-stripe rotation-orbit family produced deterministic 576-byte collisions
in an earlier digest, and a deterministic regression for that family is
kept in the test suite.  The wall absorbs the final stripe's dangling
rotated copy after the loops, so a ladder cannot march its residual off
the end of the input; constructed collisions at multiples of 32 bytes
found by SMHasher3 in a wall-less iteration are the evidence.  The
320-byte threshold bounds the four-lane path to fewer than 64 stripes, so
the full orbit exists only on the eight-lane path, where the checkpoint
interrupts it every block.

\subsection{The length in the finalizer}
\label{sec:rationale-length}

Section~\ref{sec:case} stated the two constraints: the digest must be a
pure function of the seed and the bytes read so far, or no streaming
interface can reproduce it; and the length term must separate equal-state
inputs of different lengths, or the overlapping tail reads become a
collision channel.  The chosen spelling absorbs \(nK\) inside the
\(t_0\) multiplication, satisfying both (Lemma~\ref{lem:length}) at no
additional multiplication: the multiply was already there.  Two rejected
spellings mark the boundaries.  Premixing the length into the lane initial
values, as before \texttt{v0.5}, satisfies separation but destroys purity;
the streaming state would need the total before the first byte.  XORing
\(nK\) after the final multiplications preserves purity but leaves
modular low-bit structure across lengths of equal-state keys, which
SMHasher3's SeedZeroes differentials detect; with the term inside the
multiplication, both \texttt{fmix} multiplications on the short path and
the \(K\)-multiplication in \(t_0\) stand between the length and the
output.

\subsection{Derived lane constants}
\label{sec:rationale-iv}

All eight lane initial values are derived from the premixed seed \(s\) and
shifted copies of \(K\).  Materializing eight arbitrary 64-bit literals
would cost four instructions each on AArch64 before the first byte is
absorbed; shifted copies of a constant already in a register fold into the
initialization arithmetic at compile time.  Deriving every lane from
\(s\) also seeds the full state for free: no lane starts at a value an
attacker can match independently of the seed.

\subsection{The short path}
\label{sec:rationale-short}

Inputs of at most 16 bytes get two multiplications and one strong
finalizer.  The structure exists to defeat two specific failure shapes.
First, each loaded word passes through a bijective injection before its
multiplication, so a difference confined to the top bits of a word, which
would face only a few bits of carry luck after the upward-spreading
multiply, is first copied to low positions and the difference window of
the multiplication is always wide.  Second, the two words use different
injections, different seed derivations, and different multipliers.  An
earlier iteration used the same injection on both sides; the key-to-state
maps of the two multiply terms then commuted with the rotation relating
the two seed copies, and SMHasher3 found sparse seed differences,
erasable by aligned key bits on both sides at once.  With distinct
rotation sets, simultaneous erasure requires dense key patterns that
sparse-difference key sets cannot reach.

The 1-to-3-byte load pattern, head byte plus middle and last byte packed
into disjoint bit ranges, is ChibiHash v2's; it covers every input byte
without a branch per byte, and Theorem~\ref{thm:short128} depends on that
coverage.

\subsection{Fold choices}
\label{sec:rationale-fold}

The lane folds and the finalizer combine values as
\((h \oplus \rotl(h',r))\,K\).  An additive fold could cancel exactly
against the additive structure of the absorb; an XOR of multiply-spread
values cancels only through carry luck.  The rotation amounts avoid one
specific resonance: the \(t_1\) fold uses rotation 33 because rotation 37,
the additive inverse of the absorb rotation modulo 64, re-aligned a lane's
raw stripe difference with the next lane's rotated copy at the fold, and
the aligned pair could cancel.  The upper-lane fold rotations 11, 19, 31,
47 and the finalizer rotations 13, 33, 29 are pairwise distinct and
distinct from 27 and 37.

\section{Evaluation}
\label{sec:evaluation}

\subsection{Evidence policy}

The claim register \path{paper/AUDIT.md} classifies each material
statement as code-derived, reproduced, archived, reported, or open.  A
reported result is not promoted to a result about the current snapshot
without the tested source, tool revision, command, host information, and
raw output.  Raw outputs live under \path{paper/results}, each with its
provenance header.

\subsection{Local quality harness}
\label{sec:quality}

The local C harness performs strict-avalanche measurements over input and
seed bits and exact collision checks over structured key sets.  It is
deterministic: the generator is fixed-seeded, so its numbers depend on the
digest, not the host.  For long inputs it samples 192 input-bit positions;
every avalanche cell uses 4{,}000 trials, warns above an absolute bias of
0.03, and fails above 0.045.  These are smoke-test thresholds without a
correction for all multiple comparisons.

At the current snapshot the harness reports a worst input-bit bias of
0.0360 at length 129 and a worst seed-bit bias of 0.0330 at length 4;
neither crosses its failure threshold.  All 24 structured collision sets
are clean.  The sets include sequential, sparse, high-byte-only,
zero-extension, repeated-block, text, seed-block, combination, and
rotation-orbit inputs, that is, reproductions of every failure class of
Table~\ref{tab:failures}.  The streaming differential test of
Proposition~\ref{prop:streaming} passes in the same run.  Command and
output are archived in \path{paper/results/quality.txt}.

As a control, the same harness finds 512 collisions in ChibiHash v2's
rotation-orbit set while its other 23 sets stay clean
(\path{paper/results/quality-chibihash-v2.txt}).  This does not contradict
ChibiHash's clean record in general-purpose suites; it shows that
statistical suites and construction-specific differential tests serve
different roles.  No collision observed in a finite test establishes only
that the tested set was clean.

hayahash64 leads ChibiHash v2 in every transcribed cell and in every cell
of the two archived records.  hayahash128 reaches bulk parity with
hayahash64 on both hosts and costs 0.6 to 2.3~ns over it in the
transcribed small-input cells; against the 64-bit ChibiHash v2 it leads in
most recorded cells, and every exception in the records lies below 64
bytes.

built on a widening product are faster where that product is cheap; they
use a different primitive class, which is the point of the next
measurement.

\subsection{Cross-implementation conformance}
\label{sec:conformance}

The C reference is ported to Rust, Go, Zig, Java, C\#, Python, Swift,
JavaScript, and MIPS64 assembly, each covering both digest widths.  Every
port's test suite asserts the shared known-answer vectors, the 64-bit
verification value, fixed 128-bit boundary vectors, and the invariant
\(\mathtt{hayahash128.lo} = \mathtt{hayahash64}\).  Repository CI
additionally runs a nightly differential harness that generates one
C-reference corpus, random inputs and seeds, exhaustive lengths 0 to 384,
and boundary-biased lengths through 128~KiB, and replays it through every
port; endianness is covered by an s390x big-endian known-answer run under
emulation, the ILP32 case by wasm32, and the Windows ABI by MSVC x64.

Reproduced while preparing this draft, on the drafting host: the paper's
reference check, 17 vectors for both widths plus both direct-interface
verification values; the quality harness and streaming differential; and
the Go, Rust, and Python suites.  Commands, toolchains, and results are
archived in \path{paper/results/conformance.txt}.  The remaining ports
were not run in this environment and rest on repository CI.

\section{Limitations and open work}
\label{sec:limitations}

Standing properties of the design or its stage:

\begin{itemize}
\item The algorithm is experimental.  Constants, thresholds, and digests
      may change; nothing should persist Hayahash values yet.
\item There is no cryptographic security claim, no keyed-security
      analysis, and no protection against adversarial hash-table inputs.
\item The structural lemmas of Section~\ref{sec:properties} do not bound
      collisions of the complete construction.
\item The local harness is a deterministic smoke test; SMHasher3 is a
      black-box statistical suite.  Neither bounds constructed inputs, and
      an earlier digest passed the suite while a constructed collision
      existed.
\item The streaming state buffers up to 448 bytes; callers needing a
      smaller state need a different construction.
\end{itemize}

Open work with defined completion criteria:

\begin{itemize}
\item An explicit model of the absorb recurrence and folds precise enough
      that a bound or a counterexample is checkable, and either an
      almost-universality-style bound comparable in form to PolymurHash's
      statement \cite{peters2023polymurhash} or a documented argument why
      the construction admits none.
\item A rerunnable, archived differential search over the absorb chain
      with pinned solver versions and bounds, replacing the informal
      searches in the development notes.
\item A multi-host, multi-compiler SMHasher3 sweep for the current digest
      matching the superseded \texttt{v0.4.0} nine-build record, and an
      archived raw full-suite run for both widths on bare metal.
\item Benchmark coverage for MSVC, 32-bit targets, big-endian hardware,
      and small in-order cores, and a harness revision that retains raw
      samples and an environment manifest.
\item A single generated, machine-readable vector table consumed by every
      port's test suite, replacing the current copied tables.
\end{itemize}

\section{Reproducibility}
\label{sec:repro}

From the repository root at the paper snapshot:

\begin{lstlisting}
make -C paper check          # reference vectors, quality, snapshot
make -C tests/smhasher3 run  # full suite, 64-bit registration
make -C tests/smhasher3 run HASH=hayahash128
make -B -C tests CC=clang ARCH=-mcpu=native \
  CFLAGS="-O3 -std=c11 -Wall -Wextra" run-bench
make -C paper                # build this PDF with Tectonic
\end{lstlisting}

\texttt{make -C paper check} compiles the reference check directly against
\path{hayahash.h}, reruns the quality harness, and verifies that the
snapshot register, the checkout, and the header digest agree.  The
SMHasher3 targets clone the pinned upstream commit, install the
translation, build, and run; they are separate from \texttt{check} because
they fetch and build an external tool.  Benchmark reruns require
\texttt{make -B} because the test Makefile does not track changed compiler
variables.  A paper update that changes the algorithm snapshot must update
the register, the known-answer vectors, the quality output, the affected
tables, and the claim register as one reviewable change; the procedure is
written out in \path{paper/README.md}.

\section{Conclusion}

Hayahash explores a narrow question: how fast a hash can be when limited
to portable scalar operations and the low half of 64-bit multiplication,
under the constraint of one exact digest across every implementation.
The mechanisms that answer it are a bulk loop whose carried path is one
XOR and one multiplication across eight lanes, a chained absorb that is
bijective on the stripe sequence, a length term absorbed in the finalizer,
which is what permits an exact streaming interface, overlapping whole-word
tails, and a 128-bit extraction from the same state walk whose low word is
the 64-bit digest and whose short path is injective per length.  Each
anti-collision mechanism is tied to a documented failure that produced it,
and each carries a regression.  The current evidence, a deterministic
local harness, SMHasher3 passes for both widths, benchmarks against the
closest same-class function on two systems and one WebAssembly runtime,
and nine conformant ports, justifies continued work.  It does not justify
security claims or universal quality claims, and the paper is structured
so that stronger claims can be added only together with their artifacts.
