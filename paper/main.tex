\title{Hayahash64: A Portable Scalar 64-bit Non-Cryptographic Hash}
\author{Ville Vesilehto}
\date{Working draft, \SnapshotDate}

\begin{document}

\maketitle

\begin{abstract}
Hayahash64 is an experimental, seeded, non-cryptographic hash function.
It is designed for targets that have ordinary 64-bit multiplication but
do not provide a cheap 128-bit product or useful SIMD.  The function uses a
short-input path for at most 16 bytes, four interleaved lanes for medium
inputs, and eight lanes for inputs of at least 320 bytes.  Adjacent input
words are linked by an add-and-rotate transform.  Long blocks also include a
raw-word checkpoint added after a constructed collision was found in an
earlier version.  This paper specifies the current development snapshot,
explains which parts have proofs and which do not, and records the available
quality and performance evidence.  The current snapshot passes the local
quality harness and SMHasher3's default suite, and is faster than ChibiHash v2
at most measured sizes on the two recorded systems.  There is no proof for the
complete construction and no cryptographic security claim.
\end{abstract}

\section{Status and scope}

This is a living paper for a working algorithm.  The normative artifact for
this draft is the C header at release \texttt{\SnapshotVersion}, Git commit
\texttt{\SnapshotCommit} \cite{vesilehto2026hayahash}.
The SHA-256 digest of that header is
\texttt{\SnapshotHeaderSha}.
The digest, not the commit, is what identifies the audited artifact: a
commit that leaves the header byte-identical carries every result in this
paper forward unchanged.
These values are defined once, in the register file
\path{paper/snapshot.tex}; an algorithm change updates the register, the
evaluation records, and this text as one reviewable change.

The paper describes the current snapshot only.  Earlier iterations appear
where they explain a design decision, and the project's other historical
artifacts are not audited here.  Sections marked TBD are deliberate
placeholders: each states what evidence or analysis must exist before it
can be filled in.

Hayahash64 maps a byte string and a 64-bit seed to a 64-bit result.  The
intended uses are hash tables, checksums internal to a process, and similar
non-adversarial tasks.  It is not intended for passwords, signatures,
message authentication, untrusted hash-table keys, or any use that requires
collision or preimage resistance.  The seed is an input, not a secret-key
security mechanism.

The design constraints are:

\begin{itemize}
\item unsigned 64-bit scalar arithmetic;
\item ordinary multiplication modulo \(2^{64}\), without the high product;
\item no required SIMD or architecture-specific instruction extension;
\item alignment-safe reads and a result independent of host byte order; and
\item one reference mapping across supported implementations.
\end{itemize}

The C source contains architecture- and compiler-specific scheduling choices.
These choices use the same operations and are intended to preserve the
digest.  The portability claim therefore concerns required primitives and
output, not identical source code on every target.

\section{Related work and comparison class}
\label{sec:related}

Fast non-cryptographic hashes make different choices about their required
instructions and their guarantees.  MurmurHash3 and xxHash are widely used
examples of scalar designs \cite{appleby2011murmurhash3,collet2023xxhashspec}.
wyhash and rapidhash use the folded result of a widening multiplication as a
central primitive \cite{wang2021wyhash,nicoshev2025rapidhash}.  HighwayHash
uses vector multiply and permute operations and also studies keyed security
\cite{alakuijala2016highwayhash}.  HalftimeHash takes a coding-oriented
approach to long inputs without requiring a widening 64-bit product
\cite{apple2021halftimehash}.

ChibiHash v2 is the closest baseline used here because it has the same narrow
implementation class: a small, portable, scalar 64-bit function using the low
half of ordinary multiplication \cite{nrk2024chibihash}.  This makes it a more
direct comparison than functions whose peak implementation requires a
widening product or SIMD.  The comparison does not imply that ChibiHash is
the only member of the class.

Empirical test suites and mathematical guarantees are separate evidence.
SMHasher and SMHasher3 test distribution, collisions on generated key sets,
and performance \cite{appleby2016smhasher,wojcik2022smhasher3}.  A clean run
does not prove collision resistance or rank the overall quality of two
functions.  By contrast, a construction such as PolymurHash states an
almost-universality bound under an explicit model \cite{peters2023polymurhash}.
Hayahash64 currently has no comparable bound.

\section{Contract and notation}

All state values are unsigned 64-bit words.  Addition, multiplication, and
left shift discard bits above bit 63.  Right shift is logical.  The expression
\(\rotl(x,r)\) rotates a word left by \(r\) bits.  \(\load(B,p)\) reads eight
bytes starting at offset \(p\), with the first byte as the least significant
byte.  A corresponding four-byte load is zero-extended.

The constants are:

\begin{align*}
K   &= \mathtt{9E3779B97F4A7C15}_{16},\\
M_1 &= \mathtt{3C79AC492BA7B653}_{16},\\
M_2 &= \mathtt{1C69B3F74AC4AE35}_{16}.
\end{align*}

All three constants are odd.  The input length \(n\) must be non-negative,
and the caller must provide \(n\) readable bytes.  A null pointer is permitted
only when \(n=0\).  The total length is used before any bytes are absorbed, so
the construction does not provide a natural constant-memory streaming API.

Two linear word injections are used:

\begin{align*}
\inj(w)  &= w \oplus \rotl(w,21) \oplus \rotl(w,41),\\
\injb(w) &= w \oplus \rotl(w,11) \oplus \rotl(w,50).
\end{align*}

The short-input finalizer is the \texttt{moremur} map
\cite{evensen2018moremur}:

\begin{lstlisting}
fmix(x):
    x ^= x >> 27
    x *= M1
    x ^= x >> 33
    x *= M2
    x ^= x >> 27
    return x
\end{lstlisting}

The long-input finalizer is:

\begin{lstlisting}
long_fmix(x):
    x ^= x >> 37
    x *= K
    x ^= x >> 32
    return x
\end{lstlisting}

\section{Algorithm}

\subsection{Length and seed premix}

Every path starts with
\[
    s = \mathit{seed} \oplus (nK).
\]
This puts the length and seed into the initial state.  It also distinguishes
lengths when tail reads overlap bytes that were already processed.

\subsection{Inputs of at most 16 bytes}

Two words \(a\) and \(b\) are formed without reading outside the input:

\begin{lstlisting}
if n >= 8:
    a = load64le(B, 0)
    b = load64le(B, n - 8)
else if n >= 4:
    a = load32le(B, 0)
    b = load32le(B, n - 4)
else if n > 0:
    a = B[0]
    b = (B[n / 2] << 8) | (B[n - 1] << 16)
else:
    a = 0
    b = 0
\end{lstlisting}

The two terms use different injections and multipliers:

\begin{align*}
x &= (\inj(a) \oplus s \oplus K)K,\\
y &= (\injb(b) \oplus \rotl(s,23) \oplus (K \mathbin{\gg} 19))M_1.
\end{align*}

The result is
\[
    \operatorname{fmix}(\rotl(x,27) \oplus y).
\]
The head and end reads overlap for some lengths.  This is intentional.

\subsection{Inputs longer than 16 bytes}

The common four-lane state is:

\begin{align*}
h_0 &= s \oplus K,\\
h_1 &= \rotl(s,17) + (K \mathbin{\ll} 21),\\
h_2 &= \rotl(s,34) \oplus (K \mathbin{\gg} 13),\\
h_3 &= \rotl(s,51) + (K \mathbin{\ll} 42).
\end{align*}

Let \(w_p\) be the previous raw input word, initially zero.  One stripe is
absorbed into its assigned lane as follows:

\begin{lstlisting}
absorb(h, w):
    h = (h ^ (w + rotl(wp, 27))) * K
    wp = w
\end{lstlisting}

The addition inside the parentheses happens before the XOR with the lane.
The previous word carries across lane boundaries and block boundaries.

For \(17 \leq n < 320\), complete 32-byte blocks are processed in four lanes.
Each block loads four consecutive words and assigns them to
\(h_0,h_1,h_2,h_3\) in that order.

For \(n \geq 320\), four more lanes are initialized:

\begin{align*}
h_4 &= s + (K \mathbin{\gg} 27),\\
h_5 &= \rotl(s,13) \oplus (K \mathbin{\ll} 9),\\
h_6 &= \rotl(s,26) + (K \mathbin{\gg} 40),\\
h_7 &= \rotl(s,39) \oplus (K \mathbin{\ll} 30).
\end{align*}

Each complete 64-byte block assigns eight consecutive words to
\(h_0,\ldots,h_7\).  After the eighth absorb, the raw eighth word is added to
\(h_0\):
\[
    h_0 \mathrel{+}= w_p.
\]
This checkpoint is part of the digest.  After all complete 64-byte blocks,
the upper lanes are folded into the lower lanes:

\begin{align*}
h_0 &\leftarrow (h_0 \oplus \rotl(h_4,11))K,\\
h_1 &\leftarrow (h_1 \oplus \rotl(h_5,19))K,\\
h_2 &\leftarrow (h_2 \oplus \rotl(h_6,31))K,\\
h_3 &\leftarrow (h_3 \oplus \rotl(h_7,47))K.
\end{align*}

If at least 32 bytes remain, one four-lane block is then processed.  The
previous-word chain continues from the last bulk word.

\subsection{Wall, tail, and output}

After the complete-block loops, the final previous word is observed once
more:
\[
    h_0 \mathrel{+}= \rotl(w_p,27).
\]
This operation is called the wall in the implementation.  It is a no-op when
no complete stripe was processed.

Let \(p\) be the first unconsumed byte and \(r\) the remaining length.  After
the optional four-lane block, \(0\leq r<32\) on both paths.  The tail is:

\begin{lstlisting}
if r > 16:
    h0 = (h0 + inj(load64le(B, p + 0))) * K
    h1 = (h1 + inj(load64le(B, p + 8))) * K

if r > 0:
    h2 = (h2 + inj(load64le(B, n - 16))) * K
    h3 = (h3 + inj(load64le(B, n - 8))) * K
\end{lstlisting}

The last two reads always refer to the last 16 bytes of the complete input.
They may overlap an earlier read.  At \(r=16\), only \(h_2\) and \(h_3\)
receive tail words.

The final fold is:

\begin{align*}
t_0 &= (h_0 \oplus \rotl(h_1,13))K,\\
t_1 &= (h_2 \oplus \rotl(h_3,33))K,\\
z   &= s \oplus t_0 \oplus \rotl(t_1,29).
\end{align*}

The returned value is \(\operatorname{long\_fmix}(z)\).

The threshold of 320 bytes is an algorithm parameter.  An input of exactly
320 bytes takes the eight-lane path and processes five complete bulk blocks.
Moving the threshold can change the output.

\section{Design rationale and limited analysis}
\label{sec:rationale}

\subsection{Parallel lanes}

The bulk loop uses eight independent lane states so that a processor can
overlap several multiplications.  Within a lane, the loop-carried state path
is an XOR followed by a multiplication.  The rotation operates on a raw word
that is already in a register.  Four lanes use less state for medium inputs,
where eight-lane initialization and folding would be a larger fraction of the
work.

This is a scheduling rationale, not a portable cycle-count guarantee.
Instruction latency, register allocation, and code layout vary by compiler
and target.  The C implementation therefore uses output-equivalent
specializations for selected compiler and architecture combinations.

\subsection{Injective transformed stripe sequence}

For a fixed initial \(w_{-1}\), define
\[
    t_i = w_i + \rotl(w_{i-1},27).
\]
The mapping from a word sequence \(w_0,\ldots,w_m\) to
\(t_0,\ldots,t_m\) is injective.  Suppose two input sequences first differ at
position \(j\).  Their words at \(j-1\) are equal, so their rotated terms at
position \(j\) are equal.  Addition by the same word is a bijection modulo
\(2^{64}\), so the two values of \(t_j\) differ.

This lemma concerns the transformed input sequence only.  It does not prove
that the lane recurrence, folds, or final 64-bit output are collision
resistant.  The complete function necessarily has collisions because it maps
arbitrarily long inputs to 64 bits.

\subsection{Bijective word injections and finalizers}

The maps \(\inj\) and \(\injb\) are linear over \(\mathrm{GF}(2)\).  A
rotation-XOR map with three terms corresponds to a polynomial
\(p(z)=1+z^a+z^b\) on 64 cyclic bit positions.  Over \(\mathrm{GF}(2)\),
\(z^{64}-1=(z+1)^{64}\).  Since \(p(1)=1\), \(p\) has no factor \(z+1\)
and is invertible modulo \(z^{64}-1\).  Both injections are therefore
bijections on 64-bit words.

Each XOR-right-shift step in the finalizers is also a bijection, and
multiplication by an odd constant is invertible modulo \(2^{64}\).  Thus both
finalizers are bijections.  These local properties prevent information loss
inside the named maps; they are not a proof for the full hash.

\section{Evaluation}

\subsection{Evidence policy}

The paper directory contains a claim register, \path{paper/AUDIT.md}.  Each
material statement is classified as code-derived, reproduced, archived,
reported, or open.  A reported result is not promoted to a result for the
current snapshot without the tested source, tool revision, command, host
information, and raw output.  The register covers this paper's claims about
the current snapshot; it does not audit historical project artifacts.
Section~\ref{sec:smhasher} shows the policy applied end to end: a result
reported for an earlier digest was held out of the paper until an adapter,
a pinned tool revision, and raw output existed for the current one, at which
point it was promoted rather than assumed.

\subsection{Local quality harness}

The local C harness performs strict-avalanche measurements over input and seed
bits and exact collision checks over structured key sets.  For long inputs it
samples 192 input-bit positions.  Every avalanche cell uses 4,000 trials.  The
harness warns when the largest absolute deviation from 0.5 exceeds 0.03 and
fails above 0.045.  These thresholds are simple smoke-test thresholds and do
not correct for all multiple comparisons.

At the paper snapshot, the harness reported a worst input-bit bias of 0.0403
at length 40 and a worst seed-bit bias of 0.0338 at length 256.  Neither
crossed its failure threshold.  All 24 structured collision sets were clean.
The sets include sequential, sparse, high-byte-only, zero-extension, repeated
block, text, seed-block, combination, and rotation-orbit inputs.  The exact
command and output are archived in
\texttt{paper/results/quality.txt}.

No collision observed in a finite test means only that the tested set was
clean.  It does not establish a general collision bound.

As a control, the same harness found 512 collisions in ChibiHash v2's
rotation-orbit set while its other 23 sets remained clean.  This targeted
result does not contradict ChibiHash's historical clean run in a broader
suite: the orbit regression was added after that general-purpose run.  It
shows why a statistical suite and construction-specific differential tests
serve different roles.  The control output is archived in
\path{paper/results/quality-chibihash-v2.txt}.

The runs were chosen to cover both compiled dispatch shapes.  As
Section~\ref{sec:platforms} notes, the header's
\texttt{HAYAHASH64\_\allowbreak INTERNAL\_\allowbreak TIERS} switch is 1
on AArch64 and on x86-64 under GCC, and 0 on x86-64 under Clang, so the two
shapes are different programs even though they are specified to agree.  Every
line of the three outputs that does not report a time is identical, including
each individual p-value and collision count.  The shapes therefore differ
only in speed, which is direct evidence for the exactness claim discussed in
Section~\ref{sec:implementation} and is stronger than a boundary-vector
comparison, since the suite compares many millions of digests.

The adapter, \path{tests/smhasher3/hayahash.cpp}, includes the specified
header itself rather than restating the algorithm in SMHasher3's own style.
A restatement would make the suite evidence about a copy of the function
instead of the artifact this paper specifies; the project's earlier adapter
was such a copy and still carried a stale verification value long after the
digest had moved.  SMHasher3 requires a second reader for the opposite byte
order, so the header is included twice, the second time with the host byte
order forced, which selects the header's own byte-swapping load path.
\path{tests/smhasher3/Makefile} clones the pinned commit, applies the
adapter and two portability patches, builds, and runs.  The clone is
fetched at test time rather than vendored, so SMHasher3 is not part of any
release artifact; its framework is GPL-3.0-or-later, which does not affect
the public-domain status of the header specified here, though a
redistributed combined executable would carry the GPL.  The adapter and the
two patches are themselves GPL-3.0-or-later and are excepted from this
repository's Unlicense: the patches modify GPL-covered upstream files, and
the adapter is written against SMHasher3's headers and macros and is only
ever compiled into it.  Including \path{hayahash.h} from the adapter does
not change that header's license.  One patch fixes a
\texttt{size\_t}-to-\texttt{uint64\_t\&} binding in the tool's own
random-number code that does not compile under Clang on macOS; the other
makes its build system recognize Apple Silicon, which it otherwise
classifies as an unknown processor family.  Both are applied on every host
so that all three runs build identical source, and both are archived beside
the adapter.  Both have also been submitted upstream, so the deviation from
the pinned revision is intended to be temporary rather than a fork; a future
snapshot should be able to advance the pin and drop them.

The canonical value \texttt{0xF3C4A9B4} is the same number this paper
already carried as \texttt{\SnapshotVerification}, the direct-interface
self-test value recomputed by \path{paper/tools/reference_check.c}.  That is
expected rather than a coincidence: the self-test reimplements SMHasher3's
verification procedure over the direct interface.  Its agreement with the
tool was previously an untested assumption and is now checked.

Complete raw output, including the tool's warnings, the exact commands, and
the host and compiler descriptions, is archived in
\path{paper/results/apple-m1-smhasher3.txt},
\path{paper/results/zen5-smhasher3-gcc.txt}, and
\path{paper/results/zen5-smhasher3-clang.txt}.

Two limits on what this result means.  A clean run is a statistical
black-box result: as Section~\ref{sec:related} notes, it neither proves
collision resistance nor ranks two functions, and the constructed
rotation-orbit collision found in an earlier digest after a clean run is a
concrete demonstration of that gap.  Separately, the suite's own Speed and
Hashmap sections are recorded in the archived output but are not this
paper's performance evidence; Section~\ref{sec:bench} describes the
measurements the tables use.  This paper also does not report the broad
SMHasher3 speed shootout across competitors, which would need the competitor
revisions pinned and archived as well.

A run for the earlier release \texttt{v0.2.1} reported the same 188 of 188
with verification value \texttt{0x6B558D9D}.  The digest changed between that
release and \texttt{\SnapshotVersion}, so the older result is superseded; it
was also never accompanied by an adapter or raw output in this repository.
The matching test counts reflect the size of the suite's default set, not a
result carried over.

\subsection{Benchmark method}
\label{sec:bench}

The repository benchmark compares the reference C implementations through
non-inlined wrappers with the same signature.  It reports three views:

\begin{itemize}
\item bulk throughput in decimal GB/s;
\item dependent latency, where each result becomes the next seed; and
\item independent throughput, where hashes have independent seeds.
\end{itemize}

Within one process, each cell is the median of nine calibrated samples of
approximately 40 ms.  Candidate order is rotated and periodically reversed.
The M1 values below are the median of three idle process runs.  The Zen 5 log
contains one process run and is therefore more provisional.  The benchmark
does not retain every individual sample, so distribution estimates and
confidence intervals cannot be reconstructed from the archived logs.

\texttt{-O3 -mcpu=native}.  The x86-64 run used the Zen 5 core in an AMD

      prepared to this paper's standard;
\item performance on x86-64 under Clang, which compiles a different dispatch
      shape than the measured GCC build because the straight-line length
      tiers are disabled there.  That shape is now covered for correctness by
      the Clang run in Section~\ref{sec:smhasher}, but no benchmark record
      for it exists at this paper's standard;
\item MSVC, 32-bit targets, big-endian targets, and small in-order cores,
      including the portable byte-assembly load path;
\item cache and workload distributions beyond the fixed-size benchmark; and
\item a benchmark harness revision that retains raw per-sample values and
      an environment manifest, so distribution estimates do not rest on
      process medians alone.
\end{itemize}

\section{Implementation and conformance}
\label{sec:implementation}

The reference implementation is a C99 single header.  It uses \texttt{memcpy}
for unaligned native loads and byte swaps on known big-endian hosts.  If no
byte-order macro is available, it assembles words byte by byte.  This avoids
an alignment assumption and does not silently assume little-endian order.

The source uses straight-line length tiers on selected targets, outlines the
native bulk path to manage register pressure, unrolls two bulk blocks on
AArch64 and x86-64, and keeps the WebAssembly bulk path inline.  These are
implementation choices rather than separate algorithms.  A compact
transcription is used in the Rust, Go, Zig, Java, C\#, and pure JavaScript
ports; the Python and WebAssembly fast paths compile the C header.

The paper check program contains 17 known-answer vectors covering the short,
medium, bulk, and boundary paths.  It also recomputes the direct-interface
verification value.  At this snapshot, the Rust, Go, Zig, Java, C\#, Python,
WebAssembly, and pure JavaScript suites all passed their checked-in
conformance vectors.
The commands, tool versions, and result counts are archived in
\path{paper/results/conformance.txt}.  A generator for a single
machine-readable cross-language table is still missing, so the copied tables
remain a maintenance risk.  The planned replacement (TBD) is one executable,
machine-readable model of the algorithm that generates every language-port
vector and the tables in this paper.

\section{Limitations}

Open tasks with defined completion criteria live in the TBD sections:
analysis (Section~\ref{sec:analysis}), platform coverage
(Section~\ref{sec:platforms}), and the cross-language vector generator
(Section~\ref{sec:implementation}).  The following limitations are standing
properties of the design or of its stage, not tasks:

\begin{itemize}
\item The algorithm is experimental.  Constants, the threshold, and every
      digest may change; nothing should persist hayahash values yet.
\item There is no cryptographic security claim, keyed-security analysis, or
      protection against adversarial hash-table inputs.
\item The injective stripe lemma and bijective helper maps do not prove a
      collision bound for the complete construction.
\item The local quality harness is a deterministic smoke test with simple
      thresholds, not a substitute for a broader statistical suite.
\item A clean SMHasher3 run is a black-box statistical result on the key sets
      the suite generates.  It bounds nothing about adversarial or
      constructed inputs; an earlier digest passed the suite and still had a
      constructed rotation-orbit collision.
\item The function is one-shot: the length is premixed into the initial
      state, so adapters that expose a streaming interface must buffer the
      full byte sequence or define a different construction.
\end{itemize}

\section{Reproducibility}

From the repository root at the paper snapshot:

\begin{lstlisting}
make -C paper check-reference
make -B -C tests CC=clang ARCH= \
  CFLAGS="-O2 -std=c11 -Wall -Wextra -Werror" run-quality
make -B -C tests CC=clang ARCH=-mcpu=native \
  CFLAGS="-O3 -std=c11 -Wall -Wextra" run-bench
make -C paper
\end{lstlisting}

The first command compiles the paper's reference check directly against
\texttt{hayahash.h}.  The quality command rebuilds and runs the local harness.
The forced rebuild is important because Make does not track changed compiler
variables in an existing binary.  The benchmark command regenerates medians
for the current host.  The final command builds this PDF with Tectonic.

The paper's \path{AUDIT.md} maps claims to source, command, status, and
update rule.  Raw outputs used in the tables are stored under
\path{paper/results}.  The audited commit, header digest, and verification
value are defined once in \path{paper/snapshot.tex}; the document reads
them from there, and \texttt{make -C paper check-snapshot} verifies them
against the checkout.  A paper update that changes the algorithm snapshot
must update the register, the known-answer vectors, the quality output,
and the performance results as one reviewable change.

\section{Conclusion}

Hayahash64 explores a narrow question: how fast a 64-bit non-cryptographic
hash can be when it is limited to portable scalar operations and the low half
of 64-bit multiplication.  Its main mechanisms are a two-term short path,
four- and eight-lane long paths, a chained add-and-rotate word transform,
overlapping whole-word tails, and a per-block raw-word checkpoint introduced
after a structural failure.  The current local tests and two-system benchmark
results justify continued work, but not security or universal quality claims.
The paper is structured so that stronger claims can be added only when their
artifacts are committed with the algorithm.
