OVERHEAD CALIBRATION, AND WHY THE RAW NUMBERS NEEDED CORRECTING

SMHasher3 measures the cost of calling a do-nothing hash once per process and
subtracts it from every small-key timing (tests/SpeedTest.cpp, SpeedTestInit).
That single calibration is noisy: across the 50 runs here it ranged 1.55 to
3.62 cycles. Because it is subtracted from all 31 key lengths alike, a bad
calibration shifts an entire run by a constant. On this host the hashes cost
6..18 cycles, so a 2-cycle calibration error is a 10..40% error, and an
uncorrected sweep once produced an impossible 1.59 cycles/hash for a 4-byte
rapidhash, below the latency of a single multiply.

Correction: add each run's own reported overhead back to recover the raw
measurement, then subtract one common baseline for every hash on the host.
The baseline is the smallest calibration observed, 1.55 cycles, since
interference can only inflate the do-nothing hash's measured cost, never push
it below its true value. After correction the replicate spread is at most
0.35 cycles, against +-2.08 before.

Bulk figures are uncorrected: they use a separate long-hash overhead that is
negligible against a 262144-byte hash, and they were already stable.

WHAT THE SMALL-KEY COLUMN MEASURES

timehash_small() feeds each hash's output back into the key between
iterations, so hashes cannot overlap. The column is dependent latency over
1..31-byte keys, not independent throughput, and it is not comparable to the
independent-hash figures produced by tests/bench.c.

HAYAHASH BULK IS SHAPE-DEPENDENT: 31.2 IS NOT A UNIVERSAL FIGURE

v0.4.0's fifth pass added a bulk spelling that a vectorizer can seed from,
and the effect is large but conditional. Measured on this host, same binary
family, five replicates each:

  shape                                 small (cy/hash)   bulk (B/cy)
  gcc -march=native   (tiers 1, vec 1)             12.0          31.1
  gcc -U__AVX512DQ__  (tiers 1, vec 0)             12.0          17.6
  clang++             (tiers 0, vec 0)             11.9          31.1

So a GCC build without AVX-512DQ gets 17.6 bytes/cycle, not 31. Disassembly
of hashes/hayahash.cpp.o explains it: the two fast builds each emit 8 vpmullq
(packed 64x64 multiply, an AVX-512DQ instruction, here on 256-bit ymm
registers) and the slow one emits none.

Note what that also shows: clang reaches the same rate without the special
spelling. The VECGCC gate exists to coax GCC into what clang already does on
the ordinary code, so "needs AVX-512DQ" is the real constraint and "needs
GCC" is not.
