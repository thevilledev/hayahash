COMPETITOR BUILD WIDTH: THIS IS WHY PATCH 0002 EXISTS

Upstream SMHasher3 at the pinned commit does not enable NEON on Apple
Silicon. platform/family.cmake matches CMAKE_SYSTEM_PROCESSOR against "arm"
and "aarch64", but macOS reports "arm64", so PROCESSOR_FAMILY falls through
to "Other", platform/isa.cmake never runs its ARM checks, and HAVE_ARM_NEON
is left undefined. Every hash then builds without NEON: XXH3 takes its
scalar path, and any comparison here would understate SIMD hashes.

0002-cmake-detect-apple-silicon-as-arm.patch fixes that. With it XXH3-64
reports impl "neon" rather than "scalar", and its bulk rate rises from about
7.3 to 12.6 bytes/cycle. The figures below are the patched, NEON-enabled
build. hayahash itself is unaffected either way: it contains no SIMD, and its
verification values are identical across both builds.

gxhash-64 is omitted on this host. That port only takes its hardware path
under HAVE_X86_64_AES, so on ARM it falls back to SMHasher3's software AES
and its ARM figure would describe that fallback rather than gxhash. See the
Zen 5 record for gxhash.

METHOD

./SMHasher3 --test=Speed --verbose <hash>, run round-robin across hashes
rather than five-in-a-row, so thermal drift on this fanless host affects
every hash equally. Median reported.

Replicate 1 is excluded: it ran while this machine was concurrently doing
scp, ssh and result parsing for the Zen 5 half of the comparison, and it
carries the only large outliers in the set (a5hash 17.34 against 25.6 in
every other replicate). Replicates 2-5 are used for all hashes, plus five
further idle back-to-back replicates for rapidhash, whose readings cluster at
23.8 with occasional downward excursions to 21.7-22.7; its median over nine
replicates is used.

Small-key figures are corrected for SMHasher3's once-per-process overhead
calibration, which ranged 2.64..2.99 cycles here; see the Zen 5 record for
the full explanation of that correction. Baseline used: 2.64 cycles. After
correction every hash except rapidhash has a replicate spread at or below
0.25 cycles.

The small-key column is dependent latency over 1..31-byte keys, not
independent throughput: timehash_small() feeds each hash's output back into
the key, so hashes cannot overlap. It is not comparable to the
independent-hash figures from tests/bench.c.

Full-suite pass/fail is not repeated here. The statistical tests are
deterministic given the hash, so the Zen 5 record settles it for both hosts.
