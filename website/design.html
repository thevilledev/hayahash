Design

The primitive set is exactly +, ^, <<, >>, rotl, and * mod 264 on 64-bit words. No wide product, no SIMD, no AES. This page is the whole algorithm on one screen, then the algebra behind the constants. hayahash.h stays the authoritative commentary, and the working paper carries the proofs.

Watch it run

The simulator runs the real algorithm on your input, one step at a time. Type your own text or load a preset. In the byte strip: black bytes are being read now, dark gray is the previous stripe whose rotated copy rides along, light gray is already absorbed, and an underline marks a byte read a second time by an overlapping tail read. Every value is a true 64-bit state word. The end shows both digests, and hayahash128's low word is exactly hayahash64.


The simulator needs JavaScript. The rest of this page works without it. 


        

        

        

      


      
The algorithm


      
Five constants, all odd. One of them, K, does all the
        mixing; the other four only appear in finalizers.


      
K  = 0x9E3779B97F4A7C15   floor(2^64 / phi)       the one multiplier
M1 = 0x3C79AC492BA7B653   moremur                 short path
M2 = 0x1C69B3F74AC4AE35   moremur
N1 = 0xFF51AFD7ED558CCD   MurmurHash3 finalizer   high word only
N2 = 0xC4CEB9FE1A85EC53   MurmurHash3 finalizer   high word only

inj(w)  = w ^ rotl(w, 21) ^ rotl(w, 41)      bijective
inj2(w) = w ^ rotl(w, 11) ^ rotl(w, 50)      bijective


      

        Any odd number of rotation terms is invertible over GF(2); any even
        number is not. Every path starts the same way, and the length
        appears nowhere else:
      


      
s      = seed ^ K
lenmix = n * K

Short path, n ≤ 16


      
n >= 8:  a = load64le(B, 0)   b = load64le(B, n - 8)
n >= 4:  a = load32le(B, 0)   b = load32le(B, n - 4)
n >  0:  a = B[0]             b = (B[n/2] << 8) | (B[n-1] << 16)
n == 0:  a = 0                b = 0

x = (inj(a)  ^ s           ^ K)         * K
y = (inj2(b) ^ rotl(s, 23) ^ (K >> 19)) * M1
u = rotl(x, 27) ^ y ^ lenmix

lo = fmix(u)                 hi = fmix128(x + rotl(u, 32))


      

        The head and end reads overlap for some lengths; lenmix
        is what separates those inputs. Each word gets a
        different injection before its multiply, so a difference
        confined to the top bits picks up low copies and no single key
        difference can erase the seed from both multiply terms at once.
        (u, x) is a bijection of the pre-image pair, so for a
        fixed length this path is injective in the message and, separately,
        in the seed. At exactly 16 bytes it is a permutation of the 128-bit
        space.
      


      
The absorb chain


      

        Longer inputs become 64-bit stripes. With wp the
        previous stripe, initially zero:
      


      
absorb(h, w):  h = (h ^ (w + rotl(wp, 27))) * K ;  wp = w


      

        wp chains across lanes, across blocks, and across the
        boundary between the eight-lane and four-lane loops. Two things
        follow. The map from stripe sequence to absorbed sequence is a
        bijection, so at the first stripe where two inputs differ, their
        absorbed values differ — no difference pattern can cancel
        inside the absorb. And each stripe's bits get a second, rotated life
        in the next absorb, combined by addition rather than XOR.
      


      
Lane state


      

        All eight initial values come from s and shifted copies
        of K, so the code materializes no large per-lane
        literal — on AArch64 a 64-bit literal costs four instructions
        — and full-state seeding is free.
      


      
h0 = s ^ K                      h4 = s + (K >> 27)
h1 = rotl(s, 17) + (K << 21)    h5 = rotl(s, 13) ^ (K <<  9)
h2 = rotl(s, 34) ^ (K >> 13)    h6 = rotl(s, 26) + (K >> 40)
h3 = rotl(s, 51) + (K << 42)    h7 = rotl(s, 39) ^ (K << 30)


      
Bulk block, n ≥ 320


      
one 64-byte block = 8 stripes  w0 .. w7

  t_i = w_i + rotl(w_(i-1), 27)      w_(-1) carries in from
                                     the previous block
   t0    t1    t2    t3    t4    t5    t6    t7
   |     |     |     |     |     |     |     |
   v     v     v     v     v     v     v     v
 lane0 lane1 lane2 lane3 lane4 lane5 lane6 lane7

 then: h0 += w7                      raw-word checkpoint

 per lane, per block: xor -> mul     (~4-cycle carried path)
 cross-lane mixing:   none in the loop


      

        After the last complete block the upper lanes fold into the lower,
        then at most one four-lane block runs on the remainder:
      


      
h0 = (h0 ^ rotl(h4, 11)) * K      h2 = (h2 ^ rotl(h6, 31)) * K
h1 = (h1 ^ rotl(h5, 19)) * K      h3 = (h3 ^ rotl(h7, 47)) * K


      
Wall, tail, finalizer


      
h0 += rotl(wp, 27)                   wall; no-op if no complete stripe

rho > 16:  h0 = (h0 + inj(load64le(B, p + 0))) * K
           h1 = (h1 + inj(load64le(B, p + 8))) * K
rho >  0:  h2 = (h2 + inj(load64le(B, n - 16))) * K
           h3 = (h3 + inj(load64le(B, n -  8))) * K

t0 = (h0 ^ rotl(h1, 13) ^ lenmix) * K
t1 = (h2 ^ rotl(h3, 33)) * K
z  = s ^ t0 ^ rotl(t1, 29)

lo = lfmix(z)         hi = fmix128(rotl(s, 32) ^ (t1 + rotl(t0, 47)))


      

        The last two reads always cover the final 16 bytes of the input and
        may overlap bytes already absorbed. lenmix enters
        inside the t0 multiply: XOR-ing it after the
        final multiplies also separates lengths, but leaves the difference
        in a low-order subgroup that survives to the output as modular
        structure across lengths.
      


      
Two compatible widths


      

        Both functions perform the same loads and the same state walk.
        hayahash128 returns the 64-bit result unchanged as lo,
        then extracts hi from the same state through an
        algebraically independent combine and a distinct bijective
        finalizer. Existing 64-bit digests therefore migrate without
        changing: for every input and seed,
        hayahash128(...).lo == hayahash64(...), and the second
        word costs a finalizer rather than a second pass.
      


      

        The high word combines the fold words with addition where
        the low word uses XOR, so one GF(2)-linear cancellation cannot erase
        a difference from both output paths.
      


      
Why these constants


      

        Multiplication mod 264 is the only nonlinear operation
        this primitive class offers, and it is weakest exactly where a
        difference wants to hide. Three cancellation channels exist. Each is
        closed by a specific constant, and each has a deterministic
        regression test in
        tests/quality.c.
      


      
Top-window invariance


      

        For any odd c, c * 263 =
        263. When c = 1 (mod 4) — true
        of K — the whole four-element subgroup
        {0, 262, 263, 262 +
        263} is fixed pointwise. A difference planted
        there survives every multiply unchanged, so an XOR-linked absorb
        could cancel it with a matching later difference in the same lane.
        The chained rotated copy is the answer: the same difference also
        shows up rotated, under addition, in the next absorb, and
        + and rotl commute with neither GF(2) nor
        mod-264 algebra. Cancelling both copies needs a carry
        pattern, never an identity.
      


      
Ladder return distance


      

        A carry-matched cancellation leaves a residual that walks
        r bit positions per stripe. Since
        gcd(27, 64) = 1 it visits every position with period
        64. Starting in the top window, the least d > 0 that
        brings it back is
        min{ d > 0 : rd = 0, 1, or -1 (mod 64) }:
      


      
r = 21   ->   21 * 3  = 63 = -1 (mod 64)    D = 3
r = 27   ->   27 * 19 = 513 = 1 (mod 64)    D = 19


      

        That factor of six in the number of independent carry conditions a
        ladder must satisfy is why the absorb rotation is 27 and not 21.
        Returning in the same lane of an L-lane loop
        additionally requires L to divide d.
      


      

        Three structural bounds compose with this. The four-lane loop never
        runs more than 4 * floor(319/32) = 36 chained stripes,
        short of the rotation's 64-stripe orbit. The bulk checkpoint injects
        a raw, unmultiplied stripe into lane 0 every 8 stripes, interrupting
        an orbit before it can return to its starting lane — it is
        also one reason the vectorized Zen 5 bulk shape keeps lanes 0,
        1, 6, and 7 scalar. And the wall absorbs the final stripe's dangling
        rotated copy, so a ladder cannot be terminated by placing its last
        difference past the end of the input.
      


      
Fold-rotation resonance


      

        rotl(·, r') inverts
        rotl(·, r) exactly when
        r + r' = 0 (mod 64). For r = 27 that is
        37 — which would realign a stripe difference in lane 2 with
        its own rotated copy in lane 3 at the t1 fold and allow
        exact XOR cancellation. The finalizer uses 33. For the same reason
        folds multiply rather than add: the absorb combines additively, so
        an additive fold would put a difference and its copy in one algebra,
        where cancellation is a linear condition instead of a carry
        condition.
      


      
Fixed parameters, free shapes


      

        The 320-byte bulk threshold, the absorb rotation 27, and the 64- and
        32-byte block sizes are algorithm parameters, not tuning knobs. Hash
        values change with them, and moving the threshold can push the
        four-lane path past the 36-stripe bound above.
      


      

        Dispatch shape is free: the length tiers, the loop
        unrolling, whether the bulk path is outlined, and whether a compiler
        vectorizes it are all chosen per CPU and compiler. Every shape is
        required to produce the same hash values, and a conformance run
        covers all of them at once.
        implementation.md
        lists the gates;
        smhasher3.md
        gives the build matrix.
      


      
Streaming


      

        Because the lane state depends only on the seed and the bytes seen
        so far — the length being absorbed at the finalizer — an
        incremental API can produce one-shot-identical digests without
        knowing the total up front. The state carries the eight lanes,
        wp, the seed, the running total, and a 448-byte buffer
        with a 128-byte retention floor. Bytes are consumed only in whole
        64-byte blocks in one-shot order; the floor guarantees the buffered
        suffix still holds the last 16 bytes the tail reads back; totals
        below 448 bytes stay buffered and dispatch to the one-shot function.
        Both widths match one-shot for every split of the same input.
