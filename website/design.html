Design

Four ideas make the design. The top of hayahash.h explains each idea in detail. The header stays the authoritative commentary. This page is the overview.

Watch it run

The simulator runs the real algorithm on your input, one step at a time. Type your own text or load a preset. Press Play, or step and scrub by hand. In the byte strip: black bytes are being read now, dark gray is the previous stripe whose rotated copy rides along, light gray is already absorbed, and an underline means the byte is read a second time, an overlapping tail read. Every value is the true 64-bit value. The digest at the end matches the playground and every port.


The simulator needs JavaScript. The rest of this page works without it. 


        

        

        

      


      
1. A short bulk dependency chain


      

        The bulk loop reads 64-byte blocks in 8 independent lanes. The
        loop-carried path for each lane is add → mul,
        approximately 4 cycles. No longer chain is on that path. No work
        crosses the lanes inside the loop. After the 8 stripes of a
        block, lane 0 also adds the last raw word. This is the per-block
        checkpoint. It is part of the digest, not a tuning choice.
        AArch64 folds the add into one multiply-add, so the carried path
        stays short. For comparison, ChibiHash v2 has
        an approximately 5-cycle add → mul → xor
        chain. That chain applies to each 8-byte stripe across 4 lanes.
      


      
one 64-byte block = 8 stripes  w0 .. w7   (64-bit words)

  t_i = w_i + rotl(w_(i-1), 27)      w_(-1) carries over
                                     from the previous block
   t0    t1    t2    t3    t4    t5    t6    t7
   |     |     |     |     |     |     |     |
   v     v     v     v     v     v     v     v
 lane0 lane1 lane2 lane3 lane4 lane5 lane6 lane7

 after the 8 stripes: lane0 += w7    (raw-word checkpoint)

 per lane, per block: add -> mul     (~4-cycle carried path)
 cross-lane mixing:   none in the loop. Lanes fold at the end.


      
2. A chained, injective absorb


      

        Each lane absorbs t = w + rotl(w_prev, 27). Here
        w is the current stripe. w_prev is the
        stripe before it. Compare two inputs that are not equal. Go to the
        first stripe where they differ. At that stripe,
        w_prev is equal for the two inputs. So
        t differs. By induction, the absorb sequence is
        injective.
      


      

        The rotated copy puts each stripe bit at a low position in the
        next lane. The combination of + and rotl
        is not linear over GF(2). It is not linear mod 264. The
        design sets four items against difference-ladder attacks: the
        absorb rotation amount, the fold rotations, a final "wall"
        absorb, and the per-block checkpoint. The wall absorb takes the
        last dangling stripe copy. The checkpoint adds the last raw word
        of each block into lane 0. It stops a known 64-stripe
        rotation-orbit ladder, which can delay a difference until the
        rotation returns it to its starting lane. The checkpoint is also
        one reason the vectorized bulk shape on Zen 5 keeps lanes
        0, 1, 6, and 7 scalar. The
        header notes give the details. The rotation applies to a register
        that is already loaded. It is off the loop-carried path. On wide
        cores, it costs less than a second load.
      


      
3. Derived lane constants, length in the finalizer


      

        The seed premixes into one value s. All lane IVs
        come from s plus shifted copies of the one
        multiplier constant. The code has no large per-lane literals. On
        AArch64, a 64-bit literal costs 4 instructions. Full-state
        seeding comes at no extra cost.
      


      

        The length stays out of s on purpose. It is
        absorbed in the finalizer, inside the t0 multiply.
        So the digest is a pure function of the seed and the bytes seen
        so far, and the streaming state can start hashing before the
        total length is known. len * K is injective: no
        two lengths can cancel. Absorbing it after the final multiplies
        would leave low-bit structure across lengths; SMHasher3's
        SeedZeroes differentials catch exactly that.
      


      
4. Overlapping tail reads, two-multiply short path


      

        The tail code reads whole words from the end of the input. The
        words can overlap. This is the wyhash method. No length uses a
        byte-at-a-time loop. Keys of 16 bytes or less use a special path.
        This path spreads the two loaded words with bijective 3-rotation
        injections. Each word gets a different injection. So one
        difference cannot remove the two multiply terms at the same time.
        The two words then go through independent multiplies into a strong
        finalizer.

        keeps a deterministic regression test for the rotation-orbit
        family. The
        optimization log

        these classes again.
      


      
Fixed algorithm parameters


      

        The 320-byte bulk threshold is an algorithm parameter. It is not a
        tuning knob. Hash values change with it. The four-lane mid path
        stays below 320 bytes. This keeps it below the 64-stripe orbit of
        the absorb rotation. The dispatch shape changes with the CPU and
        the compiler. Dispatch shape means the length tiers, the loop
        unrolling, and the bulk spelling. Each shape must make the same
        hash values.
        smhasher3.md
        lists the shapes. It tells you how one conformance run covers all
        of them.
