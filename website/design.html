Design

Four ideas make the design. The top of hayahash.h explains each idea in detail. The header stays the authoritative commentary. This page is the overview.

1. A short bulk dependency chain

The bulk loop reads 64-byte blocks in 8 independent lanes. The loop-carried path for each lane is add → mul, approximately 4 cycles. No longer chain is on that path. No work crosses the lanes inside the loop. For comparison, ChibiHash v2 has an approximately 5-cycle add → mul → xor chain. That chain applies to each 8-byte stripe across 4 lanes. 

one 64-byte block = 8 stripes  w0 .. w7   (64-bit words)

  t_i = w_i + rotl(w_(i-1), 27)      w_(-1) carries over
                                     from the previous block
   t0    t1    t2    t3    t4    t5    t6    t7
   |     |     |     |     |     |     |     |
   v     v     v     v     v     v     v     v
 lane0 lane1 lane2 lane3 lane4 lane5 lane6 lane7

 per lane, per block: add -> mul     (~4-cycle carried path)
 cross-lane mixing:   none in the loop. Lanes fold at the end.

2. A chained, injective absorb

Each lane absorbs t = w + rotl(w_prev, 27). Here w is the current stripe. w_prev is the stripe before it. Compare two inputs that are not equal. Go to the first stripe where they differ. At that stripe, w_prev is equal for the two inputs. Thus t differs. By induction, the absorb sequence is injective.

The rotated copy puts each stripe bit at a low position in the next lane. The combination of + and rotl is not linear over GF(2). It is not linear mod 264. The design sets three items against difference-ladder attacks: the absorb rotation amount, the fold rotations, and a final "wall" absorb. The wall absorb takes the last dangling stripe copy. The header notes give the details. The rotation applies to a register that is already loaded. It is off the loop-carried path. On wide cores, it costs less than a second load.

3. Derived lane constants

The seed and the length premix into one value s. All lane IVs come from s plus shifted copies of the one multiplier constant. The code has no large per-lane literals. On AArch64, a 64-bit literal costs 4 instructions. Full-state seeding comes at no extra cost.

4. Overlapping tail reads, two-multiply short path

The tail code reads whole words from the end of the input. The words can overlap. This is the wyhash method. No length uses a byte-at-a-time loop. Keys of 16 bytes or less use a special path. This path spreads the two loaded words with bijective 3-rotation injections. Each word gets a different injection. Thus one difference cannot remove the two multiply terms at the same time. The two words then go through independent multiplies into a strong finalizer.

Five collision classes

The hard part was to get the details right. SMHasher3 found five structural collision classes in earlier versions of this design:

  • a GF(2) nullspace in a staggered-load absorb
  • seed-copy erasure by aligned key bits, found two times
  • top-window carry-luck ladders
  • a fold rotation in resonance with the absorb rotation

The header documents each fix at its location. tests/quality.c keeps a deterministic regression test for the rotation-orbit family. The optimization log records the rejected ideas. Each of those ideas opened one of these classes again.

Fixed algorithm parameters

The 320-byte bulk threshold is an algorithm parameter. It is not a tuning knob. Hash values change with it. The four-lane mid path stays below 320 bytes. This keeps it below the 64-stripe orbit of the absorb rotation. The dispatch shape changes with the CPU and the compiler. Dispatch shape means the length tiers, the loop unrolling, and the bulk spelling. Each shape must make the same hash values. smhasher3.md lists the shapes. It tells you how one conformance run covers all of them.
