Benchmarks

You can reproduce all data on this page from the repository. All full-suite results are our own runs. They are not the published tables from upstream. We measured each shootout cell at v0.4.0, with five replicates for each hash. The hash values did not change since v0.4.0. So the numbers apply to the current release, v0.4.5.

You can also measure on your own machine. The playground compiles hayahash64, ChibiHash v2, rapidhash v3, XXH3-64, and XXH64 to one WebAssembly module and measures them in your browser.

Read these caveats first

  • * The AVX-512 condition. The 31.2 value needs vectorization. GCC vectorizes the bulk loop only when AVX-512DQ is available. AVX-512DQ has the packed 64-bit multiply. A separate sweep with five replicates ran on the same host. It gives 31.1 bytes/cycle with GCC and 31.1 with Clang. Without AVX-512DQ, GCC gives 17.6. That is less than the 28.6 of rapidhash. An EPYC 9655 shows the same 1.8× gap with GCC 13 and Clang 18. An EPYC 7B13 has no AVX-512. It cannot reach the vectorized shape with any tuning. The source stays portable scalar C in each case. No code is vectorized by hand. A machine without AVX-512 gets the lower bulk speed. Small-key speeds do not change.
  • The small-key column shows dependent latency, not throughput. SMHasher3 puts each hash value into the next key. So the hashes cannot overlap. Do not compare this column with the independent-hash numbers in the ChibiHash tables below.
  • Calibration correction. SMHasher3 measures its call overhead one time for each process. It subtracts that value from all 31 lengths. The value changed by approximately 2 cycles between runs. On Zen 5 that is 10 to 40 percent of the result. We corrected the calibration. After the correction, the five Zen 5 replicates agree to 0.35 cycles. The archived records in paper/ show the raw and the corrected numbers.
  • gxhash has numbers on Zen 5 only. Its SMHasher3 port uses the hardware path only with x86 AES. An ARM number would show a software-AES fallback, not gxhash.

The results by instruction class

  • Wide multiply: rapidhash v3 passes the suite. It is faster than hayahash on small keys on each host. On the M1 it is faster on both axes. Use rapidhash v3 when a native 128-bit multiply result is available. That instruction is exactly what the hayahash portability rules exclude. In Zen 5 bulk, hayahash is now ahead: 31.2 against 28.6 bytes/cycle. This holds only where the hayahash bulk loop vectorizes.
  • SIMD or hardware AES: these win bulk where the hardware has them. XXH3-64 reaches 48.9 bytes/cycle on Zen 5 and 12.6 on the M1. gxhash reaches 64.7 on Zen 5. Those two fail the suite. But no hash here has more speed than them.
  • Portable scalar: ChibiHash v2 is the one other hash that has the same constraints and passes. hayahash has more bulk speed on both hosts: 1.61× on the M1 and 1.99× on Zen 5. Small keys differ by CPU. On the M1, hayahash needs 11 percent less time. On Zen 5, it needs 30 percent more. There ChibiHash v2 wins the 8 to 15 byte band by approximately 5.3 cycles. mx3.v3 is the last ordinary-multiply candidate. It fails 26 tests.

Summary: compare the portable scalar hashes that pass the full suite. Among them, hayahash has the highest sustained bulk speed on both hosts. In Zen 5 bulk, hayahash is ahead of each wide-multiply hash we measured. That result needs the vectorized bulk loop. Without AVX-512DQ, the bulk speed falls to 17.6 bytes/cycle, behind rapidhash. The claims have limits: two bare-metal hosts, and the approximately 250 hashes that SMHasher3 tracks.

Comparison: ChibiHash

ChibiHash has a goal near to the hayahash goal: portable code with the ordinary multiply. So it is the most useful baseline. hayahash is its own design, not a fork. Where the header uses a ChibiHash trick, the header says so. Measure with make -C tests run-bench. The ChibiHash v1 and v2 reference sources are vendored in tests/. So the comparison is self-contained.

ChibiHash v1 wins at 8 and 16 bytes because of special paths. The same paths are part of the cause of its SMHasher3 failures. Two hashes here pass the suite: ChibiHash v2 and hayahash. Of those two, hayahash is the faster at each size. The 32 to 128 byte rows show a dispatch choice on clang targets. The compact dispatch loses 5 to 9 percent at these fixed sizes. It gains 2 to 10 percent on mixed-size workloads. A single-size table cannot show that gain. The optimization log records the measurements.

On this host, hayahash is ahead of the two ChibiHash versions at each measured size. Before the fifth optimization pass, ChibiHash v2 led the 320 to 512 byte band. That band now shows a 27 to 47 percent hayahash lead. Bulk speed at 1 MiB almost doubled when GCC vectorized the bulk loop for AVX-512. The dispatch shape changes with the CPU and the compiler. Each shape makes the same hash values.

Reproduce it

# The ChibiHash comparison. The references are vendored in tests/.
make -C tests run-bench

# SMHasher3, pinned to an exact upstream commit.
make -C tests/smhasher3 run

# The wasm32 shootout and the wasm-against-native bit-exactness check.
make -C tests/wasm run-kat run-bench

smhasher3.md tells you how to run the suite and cover all dispatch shapes. It tells you how to compute the verification values again after a change. paper/ keeps the archived raw runs for each number on this page.
