Benchmarks

Every number on this page is from our own runs at the current digest, reproducible from the repository. They are not upstream's published tables. Raw records with host, compiler, dispatch shape, and source checksums are in paper/results/.

These tables check an analytic claim rather than establish one. The bulk loop is shaped so that multiplier issue, not dependency latency, is the binding resource; that argument comes from the dependency graph and needs no measurement. The design page has it.

You can also measure on your own machine. The playground compiles hayahash64, hayahash128, ChibiHash v2, rapidhash v3, XXH3-64, and XXH64 to one WebAssembly module and measures them in your browser.

Cost of the 128-bit result

Both widths use the same state walk, and hayahash128.lo is exactly hayahash64. The extra work produces the independently combined and finalized high word. The repository harness keeps the median of nine calibrated rounds of about 40 ms on one pinned core.

Chained rows feed each result into the next seed and measure dependent latency. Independent rows allow hashes to overlap. The EPYC is virtualized, so compare 64 with 128 on that row rather than comparing its absolute speed with the bare-metal hosts.

SMHasher3 128-bit shootout

This is the current v0.5 candidate against SMHasher3 commit 51d3cd1a. Speed cells are medians of three independent, round-robin processes on the two bare-metal hosts. Small-key latency is the corrected 1 to 31 byte average; bulk is the fixed 256 KiB average. The full suite ran separately on the EPYC 9655 with 128-bit-wide expectations.

Small-key values are dependent latency, not independent throughput. Their raw process averages are corrected to one call-overhead baseline per host; the raw records contain every process value and the calculation. MeowHash has no M1 row because this implementation needs x86 AES instructions.

XXH3-128 is the bulk leader on both hosts and fails 26 of the 188 test groups. Among the passers, small-key latency favors the wide-multiply pair (a5hash, MuseAir). In Zen 5 bulk, hayahash128 reaches 31.02 bytes/cycle without a wide-result multiply or AES - past every wide-multiply passer and within 4% of AES-based MeowHash - because the outlined 128-bit dispatch is the shape GCC can auto-vectorize. On M1 it reaches 9.77 bytes/cycle, behind a5hash's 10.92 on that host.

The passing ordinary-scalar rows are hayahash128, prvhash-128, and FarmHash CC. hayahash128 leads FarmHash in bulk by 1.73× on M1 and 1.89× on Zen 5, and has lower small-key latency on both. The narrow Zen 5 result supports “fastest passing portable-scalar 128-bit hash measured here,” not a claim that no fast predecessor exists. prvhash exposes 187 applicable groups and passes all 187. See the raw records and method.

64-bit competitive data

A 64-bit competitive sweep against the wide-multiply and SIMD families — rapidhash, wyhash, komihash, a5hash, XXH3-64, gxhash, mx3 — has not been re-run since the digest changed, so this page carries none. What stands in its place is the ChibiHash comparison below: the one other hash in the sweep that meets the same portability rules and passes the suite, which is what makes it the comparison that isolates design from instruction set.

Two things are worth stating without a table. Where a native 64×64→128 multiply exists, functions built on it are the more direct choice, and rapidhash v3 is the one to reach for; that instruction is precisely what hayahash's portability rules exclude. Where it does not exist — baseline wasm being the clearest case — the ordering inverts, and the wasm table shows by how much.

Comparison: ChibiHash

ChibiHash has a goal near to the hayahash goal: portable code with the ordinary multiply. So it is the most useful baseline. hayahash is its own design, not a fork. Where the header uses a ChibiHash trick, the header says so. Measure with make -C tests run-bench. The ChibiHash v1 and v2 reference sources are vendored in tests/. So the comparison is self-contained.

ChibiHash v1 wins at 8 and 16 bytes because of special paths. The same paths are part of the cause of its SMHasher3 failures. Two 64-bit hashes here pass the suite: ChibiHash v2 and hayahash64. Of those two, hayahash64 is the faster at each size. The 32 to 128 byte rows show a dispatch choice on clang targets. The compact dispatch loses 5 to 9 percent at these fixed sizes. It gains 2 to 10 percent on mixed-size workloads. A single-size table cannot show that gain. implementation.md lists which target compiles which shape; every shape makes the same hash values.

On this host, hayahash64 is ahead of the two ChibiHash versions at each measured size, and hayahash128's long-input rate matches hayahash64 within noise: on GCC the 128-bit bulk loop is outlined, which is the shape the vectorizer can take. The 1 MiB row is where AVX-512DQ vectorization applies; the row below it is the same portable source built without it. The dispatch shape changes with the CPU and the compiler, and every shape makes the same hash values.

Reproduce it

# The ChibiHash comparison. The references are vendored in tests/.
make -C tests run-bench

# SMHasher3, pinned to an exact upstream commit.
make -C tests/smhasher3 run

# The wasm32 shootout and the wasm-against-native bit-exactness check.
make -C tests/wasm run-kat run-bench

smhasher3.md tells you how to run the suite and cover all dispatch shapes. It tells you how to compute the verification values again after a change. paper/results/ keeps the raw runs behind every table on this page, each with its host, compiler, dispatch shape, and source checksums.
