hayahash

hayahash64 and hayahash128 are portable scalar hash functions. They are not cryptographic. Both pass all 188 default tests of the SMHasher3 suite at the project's pinned revision. They stay portable:

  • They do not use SIMD.
  • They do not use a wide multiply (64×64→128 bits).
  • They have no intrinsics and no CPU-specific instructions. The header selects between portable C shapes for each compiler and CPU. The choice changes only the speed. Each shape makes the same hash values.
  • They have no undefined behavior. The C standard defines each operation in the header.
  • Byte order does not change the hash value (little-endian or big-endian).

The reference implementation is one C99 header, hayahash.h. hayahash64 has bit-exact ports to nine other languages. Haya is the stem of Japanese hayai (速い), "fast".

On the names: hayahash is the project. hayahash64 and hayahash128 are its two digest widths. They share one state walk, and the low word of hayahash128 is exactly hayahash64 for the same bytes and seed.

Use hayahash where the ordinary 64-bit multiply is the only fast path. Scalar WebAssembly and portable C are the clear cases. The JVM and .NET do expose the wide product, through Math.multiplyHigh and Math.BigMul, but how well a runtime lowers these calls varies by version. Native x86-64 and ARM64 CPUs have a wide multiply. For a 64-bit digest on those CPUs, rapidhash v3 is the better default: it is built on exactly the instruction hayahash's portability rules exclude. Take hayahash where that instruction is not there. In baseline wasm the gap runs the other way, 23.55 against 6.43 GB/s at 1 MiB in the same runtime. The benchmarks measure the trade.

Experimental. The algorithm, the constants, and the hash values can change. Do not store hash values. Do not send hash values to other systems. Do not use hayahash for security. It is not a cryptographic hash.

Portable-scalar baseline

ChibiHash v2 is the nearest comparable hash: same portability rules, same instruction set, and it passes the suite too. Comparing against it isolates design choices from instruction sets. At 1 MiB, hayahash64 reaches 30.73 GB/s against ChibiHash v2's 18.99 on the M1 Pro (1.6×), and 61.6 against 31.3 on Zen 5 with AVX-512DQ (2.0×); without AVX-512DQ the same portable source gets about 35 GB/s there.

Both loops spend the same five operations per 8-byte stripe. The difference is where the dependencies sit: hayahash carries only xor → mul per lane over eight lanes and 64-byte blocks, so multiplier issue binds before latency does. ChibiHash v2 carries a cross-lane add as well, over four lanes and 32-byte blocks, which binds on latency first. The design page has the arithmetic.

A 64-bit competitive sweep against the wide-multiply and SIMD families has not been re-run since the digest changed, so this site makes no 64-bit ranking claim beyond that baseline. The 128-bit table above is current.

You do not have to take these tables on faith. The playground compiles six hash variants to one WebAssembly module and measures them in your browser.

Quality

  • SMHasher3: 188 of 188 tests pass. The verification value is 0x65F2AC15. Every compiled dispatch shape must produce byte-identical output; one archived full-suite record exists so far, and a multi-host, multi-compiler sweep is open work. ChibiHash v2 passes the suite too. ChibiHash v1 fails it.
  • hayahash128 also passes 188 of 188 tests with 128-bit-wide expectations. Its canonical verification value is 0x3F0411F4, and its low word equals hayahash64 in the one-shot and streaming differential tests.
  • The local harness applies a strict avalanche criterion to the input bits and the seed bits. It runs exact-collision tests on 24 structured key sets. The sets include the SMHasher3 keysets that broke earlier versions of this design.
  • The nine ports are bit-exact. The test suite of each port checks the shared known-answer vectors and the verification value. A nightly differential fuzz sends a new random corpus through each language port. Each of them must return the same hash values as the C reference. The MIPS64 assembly port is not in the nightly matrix. It relies on the shared vectors.
  • CI tests byte order and ABI on big-endian s390x, ILP32 wasm32, MSVC x64, and MIPS64 under qemu. Each build must reproduce the shared vectors.

quality.md has the details and the reproduction steps. AUDIT.md tracks the evidence for each claim.

Design

  1. Eight lanes, nothing but xor → mul carried. The bulk loop takes 64-byte blocks across eight independent lanes with no cross-lane work on the loop-carried path.
  2. A chained, injective absorb. Each lane absorbs w + rotl(w_prev, 27). The stripe-to-absorbed map is a bijection, so at the first stripe where two inputs differ, their absorbed values differ. The rotated copy also gives every stripe a second life at a low position of the next absorb, under addition rather than XOR.
  3. Seed-derived lane constants; length in the finalizer. All eight lane values come from one premixed seed word plus shifted copies of the single multiplier, so there are no large per-lane literals. The length is absorbed at the end, which is what lets the streaming API match one-shot digests exactly.
  4. Overlapping tail reads, two-multiply short path. Tails read whole words from the end of the input, wyhash-style, so no length uses a byte-at-a-time loop. Keys of 16 bytes or less take a dedicated path whose 128-bit output is injective in both the message and the seed.

The hard part is that removing the wide product is not only a speed cost. It leaves multiplication mod 264 as the only nonlinear operation, and that operation is the identity on a four-element subgroup at the top of the word — so specific cancellation channels open, and specific constants close them. The design page works through the arithmetic, and its simulator runs the algorithm on your own input, one absorb at a time.
