hayahash64

hayahash64 is a 64-bit hash function. It is not cryptographic. It passes all 188 tests of the SMHasher3 suite. It stays portable:

  • It does not use SIMD.
  • It does not use a wide multiply (64×64→128 bits).
  • It has no intrinsics and no CPU-specific instructions. The header selects between portable C shapes for each compiler and CPU. The choice changes only the speed. Each shape makes the same hash values.
  • It has no undefined behavior. The C standard defines each operation in the header.
  • Byte order does not change the hash value (little-endian or big-endian).

The reference implementation is one C99 header, hayahash.h. The repository has bit-exact ports to nine other languages. Haya (速) is Japanese for "fast".

On the names: hayahash is the project. hayahash64 is its one hash function. The 64 is the width of the hash value in bits. No other widths exist yet.

Use hayahash64 on platforms that have only the ordinary 64-bit multiply. Examples: WebAssembly, the JVM, .NET, and portable C. Native x86-64 and ARM64 CPUs have a wide multiply. On those CPUs, rapidhash v3 is the better default. It is faster on small keys on each CPU we measured. On the M1, it is faster in bulk too. hayahash is ahead in bulk on Zen 5, but only with AVX-512DQ vectorization. The benchmarks measure this trade.

Experimental. The algorithm, the constants, and the hash values can change. Do not store hash values. Do not send hash values to other systems. Do not use hayahash for security. It is not a cryptographic hash.

Benchmarks

We make two claims. Each claim has limits. You can reproduce each claim:

  1. Compare the hashes that use only portable scalar 64-bit code and that pass all SMHasher3 tests. In this group, hayahash has the highest bulk speed on the two machines we measured.
  2. On Zen 5, GCC can vectorize the hayahash bulk loop. Then hayahash has more bulk speed than each wide-multiply hash we measured. This includes rapidhash v3. Only XXH3-64 and gxhash are faster in bulk there. Those two fail the suite.

No code is vectorized by hand. The small-key column shows dependent latency. Each hash value goes into the next key. Thus do not compare this column with independent-hash numbers. The data comes from our own runs at a pinned SMHasher3 commit. Each cell has five replicates, measured at v0.4.0. The benchmarks page has the full tables, the hosts, the method, and the caveats.

ChibiHash v2 is the nearest comparable hash. It has the same portability rules. It passes the suite. At 1 MiB on the M1, hayahash reaches 30.2 GB/s and ChibiHash v2 reaches 18.8 GB/s. That is a 1.6× lead. At 1 MiB on Zen 5 with AVX-512, hayahash reaches 61.3 GB/s and ChibiHash v2 reaches 31.2 GB/s. That is a 2.0× lead. Without AVX-512DQ, hayahash reaches approximately 35 GB/s there. Small keys differ by CPU. On the M1, hayahash needs 11 percent less time. On Zen 5, hayahash needs 30 percent more time.

You do not have to take these tables on faith. The playground compiles five hashes to one WebAssembly module and measures them in your browser.

Use it

You can install each port today. All ports share one version number. One release is the same algorithm in each language.

Quality

  • SMHasher3: 188 of 188 tests pass. The verification value is 0xF3C4A9B4. We verified this at v0.4.0 on nine builds. The builds span four hosts, five compilers, and the three dispatch shapes. ChibiHash v2 passes the suite too. ChibiHash v1 fails it.
  • The local harness applies a strict avalanche criterion to the input bits and the seed bits. It runs exact-collision tests on 24 structured key sets. The sets include the SMHasher3 keysets that broke earlier versions of this design.
  • The nine ports are bit-exact. The test suite of each port checks the shared known-answer vectors and the verification value. A nightly differential fuzz sends a new random corpus through each port. Each port must return the same hash values as the C reference.
  • CI tests byte order and ABI on big-endian s390x, ILP32 wasm32, MSVC x64, and MIPS64 under qemu. Each build must reproduce the shared vectors.

quality.md has the details and the reproduction steps. AUDIT.md tracks the evidence for each claim.

Design: four ideas

  1. The bulk loop has 8 independent lanes over 64-byte blocks. The loop-carried path is add → mul only.
  2. Each lane absorbs w + rotl(w_prev, 27). This absorb is injective by first-difference induction.
  3. One premixed seed and length value makes all lane constants. The code has no large per-lane literals.
  4. Tail code reads whole words that overlap, in the wyhash style. Keys of 16 bytes or less use a special two-multiply path.

The hard part was to close each structural collision class that SMHasher3 found, and to keep the speed. The design page tells more about both.
